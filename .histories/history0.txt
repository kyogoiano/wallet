Sim — e acho que isso pode ficar **muito mais interessante do que simplesmente adicionar mais endpoints à Wallet**.

O caminho que eu exploraria é criar uma arquitetura de **Wallet Core + Capability Plugins**: o core continua responsável por ledger, saldo, transferências, idempotência e consistência; funcionalidades modernas entram como módulos desacoplados que consomem eventos e, quando necessário, executam operações através de interfaces controladas.

Vou olhar rapidamente o que fintechs modernas estão efetivamente adotando para não basearmos a escolha só em tendências.


Pesquisando o cenário de 2026, eu vejo uma convergência muito clara: **wallets estão deixando de ser apenas “onde o dinheiro fica” e passando a ser uma plataforma programável de decisões e ações financeiras**.

IA financeira, Open Finance, pagamentos programáveis, controle de assinaturas, cartões virtuais e agentes capazes de executar operações aparecem como tendências concretas. ([Deloitte][1])

## Minha proposta para a nossa Wallet: **Programmable Wallet / Smart Money Plugin**

Em vez de implementarmos simplesmente, por exemplo, cashback ou round-up savings, eu criaria uma funcionalidade que aproveita muito bem a arquitetura que já estamos construindo:

> **Wallet Automation Engine**
> Um plugin que permite ao usuário — e futuramente a um AI Financial Copilot — criar regras para observar eventos financeiros e executar ações automaticamente.

Algo assim:

```text
                    ┌─────────────────────┐
                    │     Wallet Core     │
                    │                     │
                    │ Ledger              │
                    │ Transfers           │
                    │ Balance             │
                    │ Idempotency         │
                    │ Transactional Outbox│
                    └──────────┬──────────┘
                               │
                          Domain Events
                               │
                               ▼
              ┌────────────────────────────────┐
              │   Wallet Automation Platform   │
              │                                │
              │  Rule Engine                   │
              │  Policy Engine                 │
              │  Risk / Fraud Check            │
              │  Simulation                    │
              │  Execution                     │
              └───────────┬────────────────────┘
                          │
              ┌───────────┼────────────┐
              ▼           ▼            ▼
         Savings      Spending       AI Copilot
         Plugin       Plugin         Plugin
```

Acho que isso conversa **perfeitamente com o nosso projeto atual**, porque você já possui:

* ledger;
* transferências;
* idempotência;
* Transactional Outbox;
* eventos via NATS JetStream;
* motor antifraude;
* Redis para estado de alta velocidade.

Ou seja: a infraestrutura para uma feature realmente moderna já está quase toda lá.

# 1. Exemplos de automações

### Round-up automático

```text
Payment: R$ 47,30

Rule:
ROUND_UP_TO R$ 50,00

Action:
Move R$ 2,70 → Savings Wallet
```

Mas isso seria apenas o caso mais básico.

---

### Saldo inteligente

```text
WHEN balance > R$ 10.000

AND projected_cashflow_30d > R$ 3.000

THEN
    move R$ 2.000
    → Investment Wallet
```

Naturalmente, inicialmente podemos implementar uma versão simulada.

---

### Reserva automática

```text
WHEN salary_received

THEN

10% → Emergency Fund
5%  → Investment
5%  → Travel Wallet
```

Isso é basicamente **programmable money** aplicado dentro da nossa Wallet. Pagamentos programáveis e infraestrutura financeira modular estão se tornando uma direção importante do setor. ([Modern Treasury][2])

# 2. A parte realmente interessante: **Financial Copilot Plugin**

Aqui eu acho que temos algo muito mais inovador para implementar.

Em vez de o usuário criar regras manualmente:

> "Sempre que eu receber mais de R$ 5.000, guarde 10%."

Ele poderia dizer:

> **"Quero guardar R$ 20 mil em 12 meses sem comprometer meu fluxo de caixa."**

A IA não movimenta dinheiro diretamente.

Ela produz uma proposta:

```json
{
  "goal": "SAVE_R$20000",
  "deadline": "2027-08-22",

  "strategy": {
    "type": "ADAPTIVE_SAVINGS",
    "base_contribution": 1200,
    "min_balance": 3000,
    "cashflow_safety_margin": 0.20
  }
}
```

Então o sistema apresenta:

```text
Proposed Automation
────────────────────────────────

Goal:
Save R$ 20.000

Estimated completion:
11 months

Monthly contribution:
R$ 1.200

Protection:
Never reduce available balance
below R$ 3.000

[Approve]
```

Somente após aprovação:

```text
AutomationRuleCreated
```

A partir daí, **não existe IA no caminho crítico da transferência**.

Isso é importante.

# 3. Eu separaria em dois níveis

## Level 1 — Deterministic Automation

100% baseado em regras.

```text
IF event.type == MONEY_RECEIVED
AND amount > 5000
THEN transfer 10% TO savings_wallet
```

Arquiteturalmente simples e extremamente testável.

---

## Level 2 — AI-assisted Automation

A IA apenas:

```text
Natural Language
        │
        ▼
┌──────────────────┐
│ Intent Extraction │
└────────┬─────────┘
         ▼
┌──────────────────┐
│ Rule Generator   │
└────────┬─────────┘
         ▼
     Validation
         │
         ▼
    Simulation
         │
         ▼
 Human Approval
         │
         ▼
  Deterministic
    Execution
```

Isso segue uma direção que está ganhando força: interfaces financeiras baseadas em linguagem natural e agentes financeiros, mas com controles e confirmação humana para ações sensíveis. ([Stripe][3])

# 4. Como eu transformaria isso em um plugin

Eu evitaria colocar regras diretamente dentro do `WalletService`.

Criaria algo como:

```text
wallet-core
│
├── wallet-domain
├── wallet-ledger
├── wallet-application
│
├── wallet-events
│
└── wallet-plugin-api
         │
         │
         ├── savings-automation-plugin
         │
         ├── subscription-manager-plugin
         │
         ├── cashback-plugin
         │
         └── financial-copilot-plugin
```

A interface poderia começar extremamente pequena:

```java
public interface WalletPlugin {

    PluginDescriptor descriptor();

    void onEvent(WalletEvent event);
}
```

Mas eu provavelmente evoluiria rapidamente para separar:

```java
public interface WalletEventHandler<E extends WalletEvent> {

    Class<E> eventType();

    void handle(E event);
}
```

E:

```java
public interface WalletCapability {

    CapabilityDescriptor descriptor();
}
```

Assim evitamos transformar o plugin system em um "God SPI".

# Minha recomendação

Eu faria uma sequência assim:

```text
                WALLET CORE
                     │
                     ▼
          ┌─────────────────────┐
          │ Plugin / Capability │
          │        API          │
          └──────────┬──────────┘
                     │
                     ▼
      SMART SAVINGS AUTOMATION PLUGIN
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼

   Percentage      Round-Up     Threshold
                     │
                     ▼
              Goal Engine
                     │
                     ▼
            Financial Copilot
```

Isso nos dá uma evolução muito coerente:

**V1 → deterministic rules**

↓

**V2 → event-driven automations**

↓

**V3 → goal optimization**

↓

**V4 → AI suggestions**

↓

**V5 → controlled financial agent**

E, arquiteturalmente, pode virar uma espécie de **mini plataforma de fintech extensível**, semelhante ao movimento do mercado para contas financeiras modulares e embedded capabilities, em vez de uma wallet monolítica com cada feature acoplada ao core. ([Stripe][5])

Minha sugestão é começarmos pelo **ADR/arquitetura do Plugin API**, mas antes de escrever código eu faria uma comparação entre **3 candidatas**:

1. **Smart Savings & Programmable Money** — minha favorita.
2. **Subscription Intelligence** — muito próxima do que fintechs estão lançando agora.
3. **AI Financial Copilot** — mais inovadora, mas construída em cima das duas anteriores.

Podemos então escolher **uma como SPEC-XXX oficial da Wallet**, definir o bounded context, eventos, SPI, modelo de dados e roadmap de V1 a V5.
