Perfeito. Acho que agora temos material suficiente para transformar a ideia de “adicionar uma feature moderna” em uma **iniciativa arquitetural**, e não simplesmente em mais um módulo da Wallet.

O template que você anexou já nos dá uma estrutura excelente para isso — especialmente porque força **Intent → Scope → Invariants → Requirements → NFRs → Contracts → Failure Modes → Acceptance Criteria**.

Minha proposta seria **não começar imediatamente pela SPEC do Smart Savings**.

Primeiro definiria um pequeno **roadmap de evolução da plataforma Wallet**, porque a decisão sobre *plugin architecture*, MCP ou Spring AI MCP vai afetar várias features futuras.

# 1. O que seria um “plugin” na nossa Wallet?

Eu evitaria, inicialmente, um sistema do tipo:

```text
plugin.jar
    ↓
dynamic loading
    ↓
runtime reflection
    ↓
plugin executes arbitrary code
```

Isso é interessante tecnicamente, mas adiciona uma quantidade enorme de problemas:

* classloader isolation;
* version compatibility;
* dependency conflicts;
* lifecycle management;
* security boundaries;
* database migrations por plugin;
* observability;
* deployment/versioning.

Para a nossa Wallet, eu começaria com **modular capabilities**, não com OSGi 2.0.

Algo como:

```text
wallet-core
wallet-ledger
wallet-events

wallet-capability-api
        │
        ├── wallet-savings
        ├── wallet-subscriptions
        ├── wallet-cashback
        └── wallet-ai-copilot
```

Ou seja:

> Um plugin inicialmente é um módulo que implementa contratos estáveis da plataforma.

Mais tarde podemos decidir se queremos:

```text
Compile-time plugin
        ↓
Spring Module
        ↓
External Process
        ↓
Remote Capability
        ↓
Third-party Plugin
```

Essa evolução progressiva é bem mais saudável.

---

# 2. Onde o MCP entra?

Aqui está a parte que eu acho mais interessante.

Eu não usaria MCP como mecanismo interno para implementar a Wallet.

Não faria:

```text
TransferFundsService
        ↓
MCP
        ↓
Savings Plugin
```

Isso adicionaria latência e complexidade ao caminho transacional.

O MCP ficaria **na borda da plataforma**.

```text
                  ┌──────────────────┐
                  │ AI Agent         │
                  │ Claude / GPT /   │
                  │ Local Agent      │
                  └────────┬─────────┘
                           │
                     MCP Transport
                           │
                           ▼
                 ┌───────────────────┐
                 │ Wallet MCP Server │
                 │                   │
                 │ Tools             │
                 │ Resources         │
                 │ Prompts           │
                 └─────────┬─────────┘
                           │
                    Capability API
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
       Savings       Subscriptions       Analytics
```

Assim, MCP vira uma espécie de:

> **AI-facing API para a Wallet**

Enquanto nossa Capability API continua sendo:

> **Internal Domain Extension API**

Essa separação, para mim, é fundamental.

---

# 3. Spring AI MCP: provavelmente sim, mas não como primeira decisão

Como nossa stack já é Spring Boot, Spring AI MCP é uma opção muito natural.

Mas eu faria a SPEC de forma **vendor/framework agnostic**.

Por exemplo, a SPEC não deveria dizer:

```text
REQ-XXX-001:
The system SHALL use Spring AI MCP Server.
```

Melhor:

```text
REQ-XXX-001:
The Wallet SHALL expose selected capabilities
to AI agents through a standardized tool protocol.

REQ-XXX-002:
The AI integration layer SHALL remain isolated
from the Wallet domain and transaction boundary.

REQ-XXX-003:
AI-originated commands SHALL pass through
the same authorization, validation, idempotency
and fraud controls as external API requests.
```

E então, no `PLAN`, avaliamos:

```text
Option A — Spring AI MCP
Option B — Custom MCP Server
Option C — Separate MCP Gateway
Option D — REST/OpenAPI + AI Adapter
```

Minha hipótese inicial seria:

| Opção               | Minha avaliação                        |
| ------------------- | -------------------------------------- |
| Spring AI MCP       | 🟢 Excelente para o primeiro POC       |
| MCP separado        | 🟡 Melhor para isolamento futuro       |
| REST + adapter      | 🟢 Mais simples                        |
| Plugin via SSE      | 🟠 Possível, mas eu não começaria aqui |
| Dynamic JAR plugins | 🔴 Complexidade prematura              |

---

# 4. SSE transport: eu separaria do conceito de plugin

Acho que você teve uma boa intuição ao mencionar algo como:

```text
Plugin
   ↕
SSE
```

Mas eu modelaria isso como uma evolução para **Remote Capabilities**.

Por exemplo:

```text
interface Capability {

    CapabilityDescriptor descriptor();

    CapabilityResult execute(CapabilityCommand command);
}
```

Implementação local:

```text
SavingsCapability
```

Implementação remota:

```text
RemoteSavingsCapability
        ↓
HTTP / gRPC / MCP / SSE
        ↓
Savings Service
```

Assim, o Core não precisa saber se a capability está:

```text
LOCAL
REMOTE
AI-BACKED
EXTERNAL
```

Poderíamos ter:

```java
public sealed interface CapabilityEndpoint
        permits LocalCapabilityEndpoint,
                RemoteCapabilityEndpoint {
}
```

Mas eu evitaria definir isso antes de termos um caso real.

# 5. O roadmap SDD que eu sugiro

Eu criaria uma nova trilha de evolução.

## Fase 0 — Platform Foundation

### `SPEC-XXX-wallet-capability-platform.md`

Objetivo:

> Definir como novas capacidades financeiras podem ser adicionadas à Wallet sem acoplamento direto ao Core.

Essa SPEC responderia:

* Como ela recebe eventos?
* Pode executar comandos?

* Como funciona autorização?
* Como funciona idempotência?
* Como funciona isolamento?
* Como funciona versionamento?

### Invariante crítico

Eu adicionaria algo assim:

```text
I-CAPABILITY-001

No extension SHALL mutate the Ledger directly.

All monetary state transitions MUST be executed
through Wallet Core application commands.
```

Esse seria provavelmente o invariante mais importante da plataforma.

Outro:

```text
I-CAPABILITY-002

An extension MUST NOT bypass:

Authorization
Idempotency
Fraud evaluation
Ledger consistency
Transactional boundaries
```

# 7. Rules

Eu separaria Rules de Skills.

```text
├── architecture-boundaries.md

├── event-contract-policy.md
```

```text
RULE-AI-001

An LLM MUST NOT directly mutate financial state.

RULE-AI-002

All AI-generated commands MUST be represented
as typed domain commands.

RULE-AI-003

AI output MUST NOT be executed without
schema validation.

RULE-AI-004

AI-originated operations MUST pass through
the standard authorization and fraud pipeline.
```


Minha preferência arquitetural inicial seria:

```text
Wallet Core
     ↑
Capability API
     ↑
Financial Services
     ↑
AI Adapter
     ↑
MCP Server
```

e não:

```text
Wallet Core
     ↑
MCP
     ↑
Everything
```

A grande vantagem dessa sequência é que, quando chegarmos ao MCP, **já teremos ferramentas reais e bem definidas para expor**. Não estaremos procurando um problema para justificar o protocolo.

Eu começaria agora pela **SPEC da Wallet Capability Platform**, usando exatamente o seu template e mantendo os invariantes como elemento central — o template já reserva explicitamente essa seção e também contratos de interface e eventos internos, que serão cruciais para decidir o boundary entre Core, Capabilities e futura camada MCP.
