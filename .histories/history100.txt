Sim. Agora temos uma peça importante que não tínhamos na revisão anterior: o **ARCH-004 já está ratificado** e formaliza exatamente a solução que faltava para `EXECUTING`: **atomic claim + lease + recovery usando o mesmo `executionOperationId`**.

Então eu revisaria o `PLAN-004` **contra o ARCH-004 como autoridade arquitetural**, e não mais apenas contra a SPEC.

## Veredito geral

O `PLAN-004` está **conceitualmente alinhado**, mas **não está 100% convergente com o ARCH-004**.

Eu classificaria:

> 🟡 **PLAN-004 — quase pronto, mas requer uma rodada de convergence fixes antes de TASKS-004.**

E encontrei **4 bloqueadores reais** + alguns ajustes menores.

# 1. ARCH resolveu o problema do `EXECUTING` — mas o PLAN ainda não incorporou tudo

O ARCH agora define:

```text
PROPOSED
   │
   │ atomic claim
   ▼
EXECUTING
   │
   │ downstream OK
   ▼
EXECUTED
```

com:

```text
execution_claimed_at
execution_lease_until
```

e lease de 2 minutos.

O `PLAN` já tem `EXECUTING` no DDL, mas **não tem ainda**:

```sql
execution_claimed_at
execution_lease_until
```

Isso é um drift direto.

### Portanto:

**PLAN precisa incorporar:**

```sql
execution_claimed_at TIMESTAMP WITH TIME ZONE,
execution_lease_until TIMESTAMP WITH TIME ZONE
```

E o índice/consulta de recovery precisa ser definido.

---

# 2. O maior problema: `I-AI-001` ficou matematicamente incompatível com o novo lifecycle

O ARCH diz:

```text
Execute(p) iff
HumanApprove(p.id)
AND Status = PROPOSED
AND now <= expiresAt
```



Mas isso não é mais verdade depois que introduzimos:

```text
PROPOSED
   ↓ human approval + claim
EXECUTING
   ↓ crash
EXECUTING
   ↓ recovery
EXECUTED
```

Porque a **recovery legítima** ocorre quando:

```text
status = EXECUTING
```

e não:

```text
status = PROPOSED
```

### Precisamos separar duas coisas:

**Authorization invariant:**

```text
Execution MAY begin iff
HumanApproval occurred
AND proposal was valid at claim time
AND proposal was atomically claimed.
```

Depois:

```text
EXECUTING
```

é uma consequência daquela autorização.

E recovery:

```text
EXECUTING + expired lease
        ↓
same executionOperationId
        ↓
reconcile/retry
```

**não é uma nova autorização humana.**

Isso é extremamente importante.

Eu mudaria `I-AI-001` para algo conceitualmente como:

```text
I-AI-001 — Human Authorization Gate

A financial execution MUST originate from an explicit
human approval of the proposal.

Once execution ownership is atomically claimed,
subsequent retries/reconciliation MUST reuse the same
authorization and immutable executionOperationId and
MUST NOT require a new approval.
```

Esse é provavelmente o **fix mais importante** antes de TASKS.

---

# 3. `I-AI-010` precisa ser refinado

O ARCH define:

> infrastructure timeouts remain retryable under lease.

E a tabela diz:

> Proposal claim reverts to retryable state.

Aqui existe uma sutileza.

Com lease, **não precisamos necessariamente "reverter" `EXECUTING → PROPOSED`**.

Na verdade, o ARCH define:

```text
EXECUTING
    |
    | lease expires
    v
recovery
```



Então eu prefiro:

```text
EXECUTING
    |
    | lease valid
    |    → another approval = 409 / in progress
    |
    | lease expired
    ↓
reconciliation
    |
    +-- downstream already executed
    |       ↓
    |    EXECUTED
    |
    +-- not executed
            ↓
       re-dispatch same operationId
```

Ou seja:

**`EXECUTING` é retryable por recovery, não necessariamente convertido novamente em `PROPOSED`.**

Isso é mais seguro porque preserva o fato de que **a autorização já ocorreu**.

O PLAN atual diz:

> “Technical infrastructure failure → proposta reverte para PROPOSED”

Eu mudaria isso.

# 4. `parameters_hash` está no ARCH, mas não no PLAN

O ARCH explicitamente introduz:

```text
parameters_json
parameters_hash (SHA-256)
```

e diz:

> Snapshot immutability ... frozen with `parameters_hash`.

O PLAN atual tem:

```sql
parameters_json JSONB NOT NULL
```

mas não tem:

```sql
parameters_hash
```

Isso precisa ser convergido.

### DDL deveria conter algo como:

```sql
parameters_hash CHAR(64) NOT NULL
```

se o hash for armazenado como lowercase hexadecimal SHA-256.

E o PLAN deve definir que:

```text
parameters_hash =
SHA-256(canonical(parameters_json))
```

Aqui eu **não inventaria a canonicalização ainda** se ela não estiver definida em outra regra. Mas o algoritmo e a imutabilidade precisam estar alinhados ao ARCH.

# 5. Creation idempotency agora está excelente

Aqui o ARCH confirmou exatamente a decisão que queríamos.

```text

```


Isso deve entrar no PLAN como regra formal, não apenas como detalhe de implementação.

```text
same tenant + same idempotencyKey + same parametersHash

same tenant + same idempotencyKey + different parametersHash
    → 409 IdempotencyConflict
```

Esse ponto está muito bom arquiteturalmente.

# Minha decisão sobre o PLAN agora

Eu faria a seguinte classificação:

### 🟢 Fechado

* proposal domain;
* Modulith;
* tenant isolation;
* creation idempotency;
* immutable snapshot;
* `executionOperationId`;
* atomic claim;
* downstream ownership;
* business vs technical failure;
* synchronous V4 execution;
* 404 cross-tenant.

### 🟡 Corrigir antes de TASKS

1. `EXECUTING` formalmente no state machine.
2. `execution_claimed_at`.
3. `execution_lease_until`.
4. recovery/reconciliation component.
5. corrigir `I-AI-001` para não exigir `PROPOSED` durante recovery.
6. corrigir `I-AI-010` para **não depender de `EXECUTING → PROPOSED`**.
7. adicionar `parameters_hash`.
8. idempotency conflict por hash.
9. remover `core` genérico do Modulith dependency.
10. separar TTL sweeper de lease reconciler.
11. corrigir `approvalRequestId ≠ trace operationId`.
12. expandir traceability para as invariants do ARCH.

### 🔴 Não vejo mais um bloqueador arquitetural fundamental

Isso é importante: **o ARCH-004 resolveu o problema que me impedia de considerar o PLAN seguro anteriormente**.

O modelo agora é coerente:

```text
                     AI / MCP
                        │
                        ▼
                  CREATE PROPOSAL
                        │
                        ▼
                    PROPOSED
                        │
                 Human Approval
                        │
                 Atomic Claim
                        │
                        ▼
                    EXECUTING
                        │
              ┌─────────┴─────────┐
              │                   │
          downstream OK         crash
              │                   │
              ▼             lease expires
          EXECUTED                │
                                  ▼

                                  │
                         ┌────────┴────────┐
                         │                 │

                         │                 │

                     EXECUTED        retry execution
```

E isso preserva a regra central:

> **AI proposes → Human authorizes → Copilot claims execution → Domain executes → Recovery never creates a second financial operation.**

O próximo passo, portanto, **não é ainda TASKS-004**. Eu faria primeiro uma **versão corrigida do PLAN-004**, incorporando o ARCH-004 e fechando esses 12 pontos. Depois disso, aí sim podemos fazer a revisão do `TASKS-004` contra **SPEC + ARCH + PLAN**, que é exatamente o que o Stage 6 do seu pipeline exige.
