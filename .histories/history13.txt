Sim — e acho que isso deixa a SPEC-000.5 muito mais interessante. Minha recomendação seria não introduzir Neo4j como dependência obrigatória inicialmente. Podemos explorar Graph Intelligence usando uma arquitetura híbrida que aproveita o que sua Wallet já possui:

O ponto mais importante

Vector search não substitui graph analysis.

São duas capacidades diferentes:

Graph responde:
"Qual a relação entre estas contas?"
"Existe um caminho de 3 hops entre um usuário suspeito e este novo destinatário?"
Vector similarity responde:
"Quais operações/comportamentos são parecidos com este?"

Eu usaria os dois conceitos, mas sem comprar uma infraestrutura de graph database no V1.

O modelo que eu adotaria: Relational Graph + Online Graph Cache

Em vez de persistir:

(User)-[:TRANSFERRED_TO]->(User)

diretamente no Neo4j, podemos modelar relações no PostgreSQL.

pgvector: eu começaria aqui, não no Dragonfly

Minha preferência para embeddings históricos seria inicialmente:

PostgreSQL + pgvector

Porque você já possui PostgreSQL como parte do sistema.

O pgvector permite busca vetorial dentro do banco relacional e suporta HNSW e IVFFlat. HNSW tem melhor trade-off de busca/recall, mas consome mais memória e custa mais para construir; IVFFlat tende a ser mais econômico em memória/build.

Isso nos dá uma progressão natural.

Stage A — sem vector index
100 / 1.000 / 10.000 operações

Feature vectors persistidos, talvez busca exata em cenários controlados.

Stage B — HNSW

Quando similaridade se torna frequente:

CREATE INDEX fraud_embedding_hnsw
ON fraud_entity_features
USING hnsw (feature_vector vector_cosine_ops);

O pgvector também suporta halfvec, o que pode ser interessante para reduzir memória dependendo da dimensionalidade e precisão aceitável.

Stage C — Dragonfly vector

Só adotaria como alternativa se benchmarks demonstrarem que:

PostgreSQL vector latency
        >
Dragonfly hot vector latency

e houver uma carga realmente quente de similarity search.

Não devemos assumir antes do benchmark que precisamos dos dois.

Aqui acho que sua ideia é muito boa.

O primeiro modelo poderia ser algo extremamente simples:

Online Logistic Regression

Features:

x1 = transaction velocity

$$ P(fraud) = \sigma( w_0 + w_1x_1 + w_2x_2 + \dots + w_{10}x_{10} ) $$
