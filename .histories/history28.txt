# 🔴 Problema 2 — P95 < 300ms ainda é uma meta perigosa como invariant absoluto

Eu manteria o benchmark, mas não como requisito universal.

Um modelo 3B/7B local pode ter resultados radicalmente diferentes dependendo de:

* CPU
* GPU
* VRAM
* quantização
* backend
* context size
* batching
* Ollama vs vLLM vs llama.cpp

Portanto, no harness eu criaria:

```java
public record InferenceBenchmarkThresholds(
    Duration maxP95Latency,
    Duration maxTimeout,
    double minJsonValidityRate,
    double minGroundingValidityRate
) {}
```

E configuração:

```yaml
fraud:
  investigation:
    benchmark:
      balanced:
        max-p95-latency: 2s
        min-json-validity: 1.0
        min-grounding-validity: 1.0
```

Depois podemos criar perfis específicos:

```yaml
benchmark:
  ci:
    max-p95-latency: 5s

  workstation:
    max-p95-latency: 2s

  gpu:
    max-p95-latency: 300ms
```

Isso é muito mais sustentável.

# 🔴 Problema 3 — `LocalInferenceClient` não deveria estar em `internal/inference`

Na PLAN original tínhamos:

```text
internal/
    inference/
        LocalInferenceClient.java
```

Mas nas TASKS você está dizendo:

```text
NamedInterface("investigation-spi")
```

Essas duas coisas entram em conflito.

Se queremos que diferentes adapters possam implementar o SPI, o contrato não deveria ficar escondido dentro de `internal`.

Eu recomendo:

```text
br.com.wallet.fraud.investigation/

├── api/
│   ├── InvestigationService.java
│   └── model/
│
├── spi/
│   ├── LocalInferenceClient.java
│   └── StructuredInferenceRequest.java
│
└── internal/
    ├── DefaultInvestigationService.java
    ├── ClaimGroundingValidator.java
    ├── OllamaInferenceClient.java
    └── ...
```

E:

```java
@NamedInterface("investigation-api")
```

para:

```text
api
```

e:

```java
@NamedInterface("investigation-spi")
```

para:

```text
spi
```

Assim o design fica muito mais limpo:

```text
Fraud Investigation
       │
       ▼
InvestigationService API
       │
       ▼
LocalInferenceClient SPI
       │
 ┌─────┼──────────┐
 ▼     ▼          ▼
Ollama vLLM    llama.cpp
```

# 🟢 Problema 5 — Excelente decisão: magnitude preservation

Essa foi provavelmente uma das melhores evoluções do SPEC.

Antes:

```text
Raw features
     ↓
L2 normalization
     ↓
Vector
```

Problema:

```text
[0.1, 0.1, 0.1...]
```

e:

```text
[1.0, 1.0, 1.0...]
```

podem ter direção semelhante após normalização.

Agora temos:

```text
Raw Vector d
     │
     ├── L2 normalize ──► Direction
     │
     └── ||d||₂ ────────► Intensity
```

Excelente.

Eu só acrescentaria um teste explícito:

```markdown
FeatureNormalizerTest.shouldDistinguishLowAndHighIntensityProfilesWithSameDirection()
```

Por exemplo:

```text
A = [0.1, 0.1, 0.1]
B = [0.8, 0.8, 0.8]
```

Após normalização:

```text
direction(A) ≈ direction(B)
```

Mas:

```text
magnitude(A) << magnitude(B)
```

Isso garante que a decisão arquitetural nunca seja perdida em refactors futuros.

# 🟡 Problema 6 — Behavioral risk está ignorando magnitude

Atualmente:

$$
behavioral\_risk =
\max_i(similarity(v,c_i) \times w_i)
$$

Isso significa que:

```text
perfil muito fraco
```

e:

```text
perfil extremamente intenso
```

podem obter o mesmo risco se tiverem a mesma direção.

Você preservou:

```text
feature_magnitude
```

mas o risco ainda não usa isso.

Eu não necessariamente colocaria magnitude diretamente no risco agora, porque isso altera a semântica do modelo.

Mas criaria um conceito explícito:

```java
public record ArchetypeMatch(
    ArchetypeId archetype,
    double directionalSimilarity,
    double archetypeWeight,
    double behavioralIntensity,
    double weightedSimilarity
) {}
```

Assim temos:

```text
Directional similarity
        +
Behavioral intensity
```

disponíveis para o futuro `SPEC-000.8`.

Isso é especialmente importante porque **000.8 será o Signal Fusion Engine**.

Eu deixaria:

```text
SPEC-000.7
→ produces signals

SPEC-000.8
→ decides how signals are fused
```

Perfeito para o boundary.

# 🎯 Minha avaliação final

2. Corrigir o boundary do `LocalInferenceClient` para um verdadeiro **SPI**.

```text
SPEC-000.5

        ↓

        ↓

        ↓
```

```text

        │

        │
        ▼

        │
```

```text

```

Essa é, na minha opinião, a decisão arquitetural mais forte de toda a evolução do Fraud Intelligence V4.x.
