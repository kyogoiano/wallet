# 🔴 Ponto mais importante: `UNIQUE(entity_id, status)` está perigoso

Este trecho:

```sql
CONSTRAINT uq_fusion_job_pending UNIQUE (entity_id, status)
```

não implementa exatamente o comportamento desejado.

Ele impede que exista mais de um:

```text
entity_id = X
status = PENDING
```

o que parece correto inicialmente.

Mas também cria problemas porque:

* depois você só pode ter um `RUNNING` por entidade;
* um job `COMPLETED` impediria outro `COMPLETED`;
* um `FAILED` impediria outro `FAILED`.

Ou seja:

```text
UNIQUE(entity_id, status)
```

é **restritivo demais**.

## Melhor solução: Partial Unique Index

```sql
CREATE UNIQUE INDEX IF NOT EXISTS uq_fusion_job_pending_entity
ON fraud_fusion_jobs(entity_id)
WHERE status = 'PENDING';
```

Assim garantimos:

> existe no máximo um job pendente por entidade.

Enquanto podemos ter histórico:

```text
entity A
├── COMPLETED
├── COMPLETED
├── FAILED
└── PENDING   ← único ativo pendente
```

### ⭐ Eu consideraria essa mudança obrigatória.

# 🟢 Job coalescing: eu melhoraria o algoritmo

O dispatcher deveria fazer algo próximo de:

```sql
INSERT INTO fraud_fusion_jobs (
    job_id,
    entity_id,
    model_version,
    status,
    as_of,
    payload,
    created_at,
    updated_at
)
VALUES (
    :jobId,
    :entityId,
    :modelVersion,
    'PENDING',
    :asOf,
    CAST(:payload AS jsonb),
    NOW(),
    NOW()
)
ON CONFLICT (entity_id)
WHERE status = 'PENDING'
DO UPDATE SET
    as_of = EXCLUDED.as_of,
    payload = EXCLUDED.payload,
    model_version = EXCLUDED.model_version,
    updated_at = NOW();
```

Isso implementa exatamente:

> **latest state wins while pending**

Que é ideal para fraude comportamental.

Você não precisa calcular:

```text
evento 1
evento 2
evento 3
evento 4
```

se todos chegaram antes do worker processar.

Você processa:

```text
estado da entidade após evento 4
```

# 🔴 Outro ponto: precisamos definir o comportamento durante `RUNNING`

Imagine:

```text
Worker:
entity A → RUNNING
```

Durante a execução:

```text
Event 1
Event 2
Event 3
```

Não podemos atualizar silenciosamente o job `RUNNING`.

Minha recomendação:

```text
PENDING
   ↑
   │ coalesce
   │
Dispatcher

RUNNING
   │
   ├── novo evento?
   │
   └── cria/atualiza novo PENDING
```

Portanto:

```text
RUNNING job
+
new event
=
new PENDING job
```

Isso preserva o processamento atual e garante que haverá uma nova avaliação depois.

# 🟢 A arquitetura de correlação está conceitualmente correta

Este ponto foi uma grande melhoria:

```text
Graph
     \
      → Correlation Group → Master Fusion
     /
Propagation
```

Porque `graph_risk` e `propagated_risk` não são completamente independentes.

A fórmula:

$$
R_{gg}
=
1-(1-R_g)(1-w_pR_p)
$$

é razoável.

Depois:

$$
R_{final}
=
1-
(1-R_d)
(1-w_gR_{gg})
(1-w_bR_b)
(1-w_mR_{ml})
$$

Isso evita uma fusão ingênua:

```java
direct + graph + propagation + behavioral + ml
```

que explodiria facilmente para `> 1`.

# 🟢 Direct Rule Primacy está muito bem definido

Eu manteria explicitamente:

```java
if (signals.directRisk() >= 1.0) {
    return RiskFusionResult.hardBlock(...);
}
```

Mesmo que matematicamente:

$$
1-(1-1.0)\cdot X = 1.0
$$

o `HardRulePolicy` explícito é importante semanticamente.

Porque:

```text
R_direct = 1.0
```

não significa apenas:

> "risco muito alto"

Significa:

> **uma regra determinística declarou uma violação não negociável.**

Portanto:

```text
HARD_BLOCK
```

deve ser semanticamente diferente de:

```text
R_final = 0.99
```

Excelente decisão no plano.

# 🟢 Leave-One-Out Attribution é uma escolha muito boa

Gostei bastante dessa decisão.

A fórmula:

$$

é muito melhor que tentar simplesmente usar:

```text
signal × weight
```

porque a sua fusion é não linear.

Exemplo:

```text
Graph contribution ≠ graphRisk × graphWeight
```

necessariamente.

LOO mede o efeito real daquele fator no resultado final.

# Minha conclusão

**O PLAN-000.8 está arquiteturalmente muito forte.** Eu diria que ele está em um nível superior ao plano original baseado diretamente em LangGraph.

A decisão mais importante foi esta:

> **usar LLM/SLM como componente especializado de investigação (SPEC-000.7), mas manter fusion, decisão, workflow, estado e auditoria em Java determinístico.**

Isso cria uma separação muito saudável:

```text
QUANTITATIVE RISK
      ↓
deterministic Java
      ↓
FraudDecision
      ↓
qualitative investigation
      ↓
grounded SLM
      ↓
human analyst
```

Eu faria os cinco ajustes acima e então partiria para o **TASKS-000.8 em TDD order**.

E, sinceramente, a próxima task breakdown deveria colocar a **fila durável e o RiskFusionEngine antes do ONNX**, porque isso permite construir todo o pipeline com um `MlSignalProvider` fake antes de introduzir o runtime ONNX. Isso reduz bastante a complexidade inicial.
