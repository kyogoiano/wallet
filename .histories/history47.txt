# 4. TASK-PRC-3.3: good, but there's an important interpretation

You implemented:

```java
FileChannel.tryLock()
```

on:

```text
.spool.lock
```

That's correct for **single-writer protection of one journal directory**.

But it must not accidentally become:

> only one Edge instance may exist.

The intended topology should be:

```text
Edge-1
  └── /spool/edge-1/

Edge-2
  └── /spool/edge-2/

Edge-3
  └── /spool/edge-3/
```

not:

```text
Edge-1 ─┐
Edge-2 ─┼── /shared/spool/
Edge-3 ─┘
```

because your journal is explicitly **node-local durability**, not a distributed queue.

So I'd add a test:

```text
SpoolLockFileTest.shouldRejectSecondWriterForSameSpool()
```

and a deployment invariant:

```text
Each Edge runtime MUST own an exclusive local journal directory.
A journal directory MUST NOT be shared concurrently between Edge instances.
```

That is an important distinction.

# 6. Core status is the biggest architectural concern

This is where I'd spend the most attention.

You currently have:

```text
CoreCommandConsumer
       │
       ▼
CoreStatusPublisher
       │
       ▼
operations.status.<operationId>
       │
       ▼
OperationStatusHub
       │
       ▼
SSE
```

That's good for **live distribution**.

But NATS status publication is not necessarily sufficient as the **durable source of current operation state**.

You already recognized this in the previous 000.9 design.

Imagine:

```text
Core
 │
 ├── transaction commits COMPLETED
 │
 ├── publishes NATS status
 │
 X
Edge crashes
```

or:

```text
Core
 │
 ├── publishes status
 │
 X
NATS consumer/fanout unavailable
```

A later SSE client needs:

```text
GET /operations/{operationId}
```

or an equivalent:

```text
DurableOperationStatusProvider
```

to obtain the current state.

Your task matrix mentions:

> `Dropped status message -> Edge SSE fallback query`

but **there is no actual implementation task for the durable status provider in the task list.**

That's a gap.

### I'd add

```text
TASK-PRC-5.2 [MUST]
Implement DurableOperationStatusProvider SPI and ensure SSE
bootstraps current durable operation state before subscribing
to live OperationStatusHub events.
```

Then:

```text
TASK-PRC-5.3 [MUST]
RED: SSE reconnect after dropped NATS status event
GREEN: durable bootstrap + live fanout
```

This is more important than several of the deployment details.

with:

```text

```

actually published and consumed through the configured stream.

This prevents another subtle subject topology bug.

# 8. TASK-PRC-4.3 needs idempotency awareness

You have:

> broadcast status via `CoreStatusPublisher` upon use case execution completion.

But Core is consuming JetStream, therefore:

```text
at-least-once delivery
```

means potentially:

```text
Command
   ↓
Core
   ↓
financial transaction commits
   ↓
status COMPLETED published
   ↓
ACK lost
   ↓
same command delivered again
```

Financial idempotency protects the ledger.

But status publication should also be **idempotent or semantically monotonic**.

You should ensure:

```text
COMPLETED
COMPLETED
COMPLETED
```

doesn't create problematic state transitions.

And never:

```text
COMPLETED
   ↓
FAILED
```

for the same operation because of a duplicate/late processing path.

I'd add a test around terminal-state monotonicity.

# 11. TASK-PRC-6.2 graceful shutdown is good, but verify message semantics

This is another place where the task could be more precise.

During SIGTERM:

```text
stop accepting new ingress
       ↓
drain in-flight work
       ↓
flush journal batch
       ↓
finish/persist current operation
       ↓
ACK only completed NATS messages
       ↓
shutdown
```

The dangerous behavior would be:

```text
SIGTERM
  ↓
ACK
  ↓
process dies
```

before the financial effect is durable.

So I'd add explicit tests:

```text
GracefulShutdownIT.shouldNotAckUnprocessedCommand()
GracefulShutdownIT.shouldAckOnlyAfterFinancialEffect()
GracefulShutdownIT.shouldFlushJournalBeforeTermination()
```

Your existing task says "flush batch", which is good, but the **ACK semantics** are even more important.

## One more important observation

The fact that **all implementation tasks are `[x]` but the convergence checklist is still `[ ]` is actually correct**.

Don't change those checklist items to `[x]` just because the implementation exists.

You have two different states:

```text
Implementation complete
        ≠
Architecture verified
```

That's exactly what the convergence phase should prove.

So I'd keep:

```text
TASKS = [x]
CONVERGENCE = [ ]
```

until the real build/integration/architecture tests have been executed.

### Final verdict

I would classify the current TASKS-000.9.1 as:

**🟢 Implementation-ready / largely implemented, with a small convergence gap.**

The two areas I'd treat as **MUST-fix before declaring 000.9.1 closed** are:

1. **Durable operation status recovery** — NATS status fanout cannot be the sole source of truth for SSE.
2. **Spec/task traceability reconciliation** — the newer `REQ-PRC-014..016` and invariants need to exist in SPEC-000.9.1 if `I-SDD-003` really means 100% reconciliation.

Everything else is mostly hardening rather than architectural rework.
