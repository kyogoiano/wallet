## One change I would still make: `REQ-PRC-020` wording

Your task says:

> `NOT_FOUND` maps to in-flight processing

That's reasonable, but there's an important semantic distinction.

`NOT_FOUND` can mean:

1. the operation hasn't reached Core yet;
2. the operation is currently being processed but state hasn't been persisted;
3. the operation ID is genuinely unknown/invalid.

Those aren't necessarily equivalent.

So I would avoid making:

```text
NOT_FOUND → IN_FLIGHT
```

an unconditional semantic rule.

I'd instead define:

```text
QUERY_NOT_FOUND
    ↓
operation state unavailable
    ↓
SSE may represent "PROCESSING / UNKNOWN"
```

unless Core has a stronger invariant proving that every accepted operation must eventually have a durable operation record.

If `WalletOperationsDao` already guarantees that operation state is created atomically with command acceptance, then your current behavior is fine. **The task document itself doesn't establish that guarantee**, so I'd leave the distinction explicit.

# The other important thing: test `DEGRADED_UNAVAILABLE` as a client-visible state

You have:

```text
timeout → DEGRADED_UNAVAILABLE
```

and the convergence gate says:

> query timeout emits degraded response without hanging

Good.

But I'd make sure the test verifies **both sides**:

```text
NATS Request/Reply timeout
        ↓
NatsDurableOperationStateProvider
        ↓
DEGRADED_UNAVAILABLE
        ↓
SSE/API
        ↓
client gets explicit degraded state
```

rather than simply asserting that an exception doesn't occur.

The architectural principle should be:

> **Never fabricate current operation state when the authoritative state cannot be reached.**

That's especially important for a financial system.

# One potential naming inconsistency

Your matrix says:

```text
REQ-PRC-014 → I-GRACEFUL-001
```

while:

```text
REQ-PRC-022 → I-GRACEFUL-001
```

also exists.

That's not wrong, but I'd make the distinction clearer:

```text
I-GRACEFUL-001
  ├── shutdown lifecycle
  └── ACK safety
```

or introduce something like:

```text
I-ACK-001
```

for:

> Never ACK a command before the financial effect is durable.

I actually prefer the latter because ACK safety is broader than SIGTERM. It applies to:

* normal processing
* crashes
* exceptions
* shutdown
* consumer rebalance
* process termination

So:

```text
I-GRACEFUL-001
    graceful lifecycle

I-ACK-001
    ACK only after durable financial effect
```

would be architecturally cleaner.

This isn't necessary if you want to minimize scope, though.

# Final task structure

At this point the architecture is essentially:

```text
                ┌─────────────────────┐
                │       EDGE          │
                │                     │
HTTP/QUIC ─────►│ EdgeApplication      │
                │     │               │
                │     ├── Journal      │
                │     ├── SSE Hub      │
                │     └── NATS         │
                └─────┼───────────────┘
                      │
                JetStream IPC
                      │
                ┌─────▼───────────────┐
                │       CORE          │
                │                     │
                │ CoreApplication      │
                │     │               │
                │     ├── Consumer     │
                │     ├── Ledger       │
                │     ├── Operation DB │
                │     └── Status       │
                └─────────────────────┘
```

And status recovery:

```text
Core
 │
 ├── durable operation state ── PostgreSQL
 │
 └── live status ── NATS ──► Edge SSE
                         ▲
                         │
                 dropped event?
                         │
Edge ── Request/Reply ───┘
          operations.query.<id>
```

That is a **very solid separation**.

### My recommendation

I would make only these final edits:

1. Clarify `NOT_FOUND` semantics.
2. Ensure `DEGRADED_UNAVAILABLE` is explicitly client-visible.
3. Optionally split `I-GRACEFUL-001` from a general `I-ACK-001`.
4. Make the exact duplicate-operation/dropped-status scenario explicit in `TASK-PRC-7.3`.

Then **freeze SPEC/TASKS-000.9.1** and move to the implementation/convergence phase rather than continuing to architecturally expand it.

At that point, the next artifact I would review is **PLAN-000.9.1**, because the task set is now sufficiently stable that the plan should be checked for any ordering/dependency mismatch before you spend more implementation effort.
