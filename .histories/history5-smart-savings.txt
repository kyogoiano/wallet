Gostei bastante da direção da `SPEC-001`. Ela está **muito mais concreta e melhor posicionada** agora que a `SPEC-000` já estabeleceu o baseline do Modulith.

Minha avaliação: **Draft / Clarification é exatamente o status correto**. Eu não ratificaria ainda, mas não por causa da arquitetura principal — ela está boa. Há alguns pontos importantes de semântica financeira e de integração que precisamos fechar antes do Gate 1.

## Visão geral

A arquitetura pretendida está correta:

```text
                    ledger
                       │
                       │ DepositCompletedEvent
                       │ TransferCompletedEvent
                       ▼
                ┌──────────────┐
                │   savings    │
                │              │
                │ observe      │
                │ analyze      │
                │ decide       │
                └──────┬───────┘
                       │
                       │ TransferFundsUseCase
                       ▼
                ┌──────────────┐
                │    ledger    │
                │              │
                │ authorize    │
                │ fraud        │
                │ idempotency  │
                │ execute      │
                └──────────────┘
```

Isso respeita perfeitamente o mantra:

> **Capabilities observe, analyze, and decide. The Financial Core authorizes and executes.**

Eu manteria isso como princípio central da SPEC.

---

# 1. Primeiro ponto crítico: `TransferCompletedEvent` não significa necessariamente “spend”

Hoje temos:

```text
TransferCompletedEvent
    ↓
Round-Up
```

Mas uma transferência pode ser:

```text
Wallet A → Wallet B
Wallet A → Own Savings Wallet
Internal transfer
External transfer
Capability-generated transfer
```

Então precisamos definir **quais transfers são elegíveis para round-up**.

Eu adicionaria algo como:

### `REQ-SAV-002A — Eligible Transaction Classification`

> The Round-Up rule SHALL only evaluate outgoing transactions classified as user-originated eligible spending or transfers. Transfers generated by automated capabilities, reversals, corrections, or explicitly excluded transaction types SHALL NOT trigger round-up evaluation.

Idealmente o evento deveria carregar metadata suficiente:

```java
public record TransferCompletedEvent(
    UUID operationId,
    UUID sourceWalletId,
    UUID destinationWalletId,
    Money amount,
    TransferOrigin origin,
    TransferPurpose purpose
) {}
```

Por exemplo:

```java
public enum TransferOrigin {
    USER,
    SAVINGS_AUTOMATION,
    SYSTEM,
    REVERSAL
}
```

Assim o loop prevention fica muito mais robusto do que tentar inferir tudo a partir de um hash de `operation_id`.

---

# 2. Eu mudaria o mecanismo de loop prevention

Atualmente:

```text
SHA256(
    sourceOperationId
    + ruleId
    + SAVINGS_SWEEP
)
```

é ótimo para **idempotência determinística**.

Mas eu não usaria isso como o único mecanismo de classificação.

Eu separaria dois conceitos.

## Idempotência

```text
operation_id =
SHA256(
    source_operation_id
    + rule_id
    + action_type
)
```

## Origem da operação

```text
origin = SAVINGS_AUTOMATION
```

Então:

```text
TransferCompletedEvent
        │
        ▼
origin == SAVINGS_AUTOMATION?
        │
   YES ─┴──→ ignore
        │
       NO
        ▼
evaluate round-up
```

Muito mais explícito.

Portanto eu reescreveria o invariante:

### `I-SAVINGS-001`

> Savings-generated monetary commands MUST use a deterministic operation identifier derived from the triggering operation and rule. Savings-generated commands MUST also be explicitly classified as `SAVINGS_AUTOMATION`. Events originating from this classification SHALL NOT trigger additional savings evaluation.

Isso separa:

```text
Idempotency ≠ Causality ≠ Origin
```

E isso será extremamente útil quando tivermos:

```text
savings
goals
subscription automation
AI proposals
```

---

# 3. O Threshold Sweep tem uma ambiguidade importante

Este trecho:

> Limit R$ 10,000.00, Balance R$ 12,500.00 → Save R$ 2,500

parece simples, mas precisamos decidir **quando o balance é observado**.

Imagine:

```text
Initial balance: R$ 9,500
Deposit:         R$ 5,000
```

Após o depósito:

```text
Balance = R$ 14,500
```

Threshold:

```text
R$ 10,000
```

Sweep:

```text
R$ 4,500
```

Correto.

Mas se houver concorrência:

```text
Deposit A
Deposit B
Transfer C
```

o evento pode ser processado depois que o balance já mudou.

Portanto, a SPEC precisa decidir:

### Opção A — Snapshot event

O evento carrega:

```text
balanceAfterOperation
```

### Opção B — Current balance

O Savings consulta:

```java
BalanceUseCase.getBalance(walletId)
```

no momento da avaliação.

Eu recomendo **Opção B** para V1, mas com semântica explícita:

> Threshold Sweep evaluates the currently available balance at the time of asynchronous processing. It does not guarantee execution against the balance immediately following the triggering transaction.

Então a automação continua correta mesmo com processamento assíncrono.

---

# 4. O `I-SAVINGS-004` precisa considerar melhor o modelo de concorrência

Hoje:

> MUST NOT execute if it would cause source account balance to drop below zero

Tecnicamente, isso já deve ser garantido pelo `ledger`.

O Savings não deveria tentar reproduzir a regra financeira.

Eu mudaria para:

> The Savings module MAY calculate an intended sweep amount based on available business context, but the Financial Core remains the authoritative enforcement point for balance non-negativity and transfer validity.

Então:

```text
Savings
   │
   │ proposed amount
   ▼
Ledger
   │
   ├── sufficient funds?
   ├── minimum constraints?
   ├── authorization?
   ├── fraud?
   └── execute / reject
```

Para `minimum retained balance`, entretanto, há uma questão diferente.

Essa é uma **regra de negócio da savings plan**.

Então:

```text
currentBalance
      │
      ▼
maximumSweep =
currentBalance - minimumRetainedBalance
```

E:

```text
actualSweep =
min(calculatedSweep, maximumSweep)
```

Mas o ledger continua sendo a autoridade final.

Eu reformularia:

### `I-SAVINGS-004 — Liquidity Intent Protection`

> The Savings module SHALL never intentionally request a sweep exceeding the current balance minus the configured minimum retained balance. Final balance validity remains exclusively enforced by the Financial Core.

---

# 5. O Percentage Sweep precisa definir arredondamento monetário

Temos:

```text
5000 × 10% = 500
```

Fácil.

Mas:

```text
R$ 101.01 × 10%
```

gera:

```text
R$ 10.101
```

Precisamos definir:

```text
R$ 10.10 ?
R$ 10.11 ?
```

Eu adicionaria:

### `REQ-SAV-004A — Monetary Rounding`

> All savings calculations SHALL use the Wallet monetary representation and its canonical currency rounding rules. No floating-point arithmetic SHALL be used.

Por exemplo:

```java
Money amount;
BigDecimal percentage;
```

e uma regra explícita de rounding.

Isso é Gate 1 obrigatório para mim.

---

# 6. Round-Up: precisamos definir validação do `step`

Exemplo:

```text
47.30 → 50.00
```

Mas precisamos formalizar:

```text
step > 0
```

E talvez:

```text
step ∈ {1, 5, 10, 50}
```

ou permitir qualquer incremento monetariamente válido.

Além disso:

```text
47.30
step = 0.01
```

gera:

```text
sweep = 0
```

Então eu adicionaria:

### `REQ-SAV-003A`

> The round-up increment SHALL be strictly positive and compatible with the currency precision. A calculated sweep amount equal to zero SHALL NOT dispatch a financial command.

---

# 7. “One or more rules per wallet” pode gerar efeitos inesperados

Hoje:

> Users SHALL be able to configure one or more active savings rules per wallet.

Imagine:

```text
Deposit R$ 10,000

Percentage 10%:
→ R$ 1,000

Threshold R$ 8,000:
→ R$ 2,000
```

Total:

```text
R$ 3,000
```

Isso é esperado?

Talvez.

Mas e:

```text
Percentage = 90%
Threshold = R$ 500
```

Temos múltiplas regras concorrendo pela mesma liquidez.

Eu sugiro definir uma das seguintes políticas:

### Opção A — Independent Rules

Cada regra calcula e executa independentemente.

### Opção B — Ordered Rules

```text
1. Percentage
2. Threshold
3. Round-Up
```

### Opção C — Savings Plan Budget

O plano calcula o conjunto de ações antes de executar.

Para a primeira capability, eu escolheria:

> **Ordered deterministic evaluation.**

Por exemplo:

```text
Deposit
   │
   ▼
Percentage Sweep
   │
   ▼
Threshold Sweep
```

Cada etapa usa o estado disponível mais recente.

Isso evita duas regras simultâneas assumindo que possuem o mesmo saldo.

---

# 8. Eu reconsideraria a meta de `< 2 ms`

A regra em memória pode ser:

```text
O(1)
```

mas a capability inteira pode envolver:

```text
event persistence
database lookup
SavingsPlanDao
balance query
transfer dispatch
```

Portanto:

```text
Rule calculation < 2 ms
```

👍

Mas:

```text
Savings event processing < 2 ms
```

provavelmente não é um contrato útil.

Eu escreveria:

> Pure deterministic rule evaluation SHALL complete within 2 ms under the defined benchmark workload. Persistence, event delivery, Financial Core execution, and external dependencies are excluded from this measurement.

# 9. Atenção ao uso de baggage para `rule_id`

Eu manteria:

```text
savings.rule_id
savings.source_operation_id
```

como atributos/metadata de tracing.

Mas evitaria transformar tudo em baggage global se esses valores não precisam atravessar todos os downstream services.

Eu faria:

```text
Span Attributes
```

para:

```text
savings.rule_id
savings.rule_type
savings.source_operation_id
savings.sweep_amount
```

E manteria o `operation_id` como o contexto de correlação principal.

Ficaria algo assim:

```text
Trace
 └── operation_id
       │
       └── Savings Sweep Span
              ├── savings.rule_id
              ├── savings.rule_type
              ├── savings.source_operation_id
              └── savings.sweep_amount
```

# 10. A maior decisão que falta: o que é uma Savings Wallet?

A SPEC fala:

> transfer to Savings Wallet

Mas precisamos definir o modelo.

### Opção A — Wallet separada

```text
User
 ├── Primary Wallet
 │
 └── Savings Wallet
```

### Opção B — mesma wallet, contas internas

```text
Wallet
 ├── AVAILABLE
 └── SAVINGS
```

### Opção C — wallet vinculada por `SavingsPlan`

```text
SavingsPlan
    sourceWalletId
    targetWalletId
```

Para a arquitetura atual, eu gosto da **Opção C**.

```java
public record SavingsPlan(
    UUID id,
    UUID sourceWalletId,
    UUID targetWalletId,
    List<SavingsRule> rules
) {}
```

Porque não introduz uma nova semântica no Ledger.

Para o Ledger:

```text
TransferFunds(
    sourceWalletId,
    targetWalletId,
    amount
)
```

é apenas uma transferência normal.

Para o Savings:

```text
source → target
```

é uma regra automatizada.

Isso é bem limpo.

# Minha versão proposta dos esclarecimentos do Gate 1

Antes de ratificar a SPEC, eu fecharia estas decisões:

| ID             | Decision                                                                     |
| -------------- | ---------------------------------------------------------------------------- |
| `CLAR-SAV-001` | Quais `TransferCompletedEvent` são elegíveis para Round-Up?                  |
| `CLAR-SAV-002` | Como eventos carregam `origin` / causality metadata?                         |
| `CLAR-SAV-003` | Threshold usa balance snapshot ou current balance?                           |
| `CLAR-SAV-004` | Qual a política de arredondamento monetário?                                 |
| `CLAR-SAV-005` | Como múltiplas regras concorrem pela mesma liquidez?                         |
| `CLAR-SAV-006` | O Savings Wallet é uma wallet existente vinculada ao plano?                  |
| `CLAR-SAV-007` | Qual é a semântica de retry após falha do listener/sweep?                    |
| `CLAR-SAV-008` | Savings execution history é apenas audit trail ou participa da deduplicação? |

## Minha recomendação

Eu fecharia assim para V1:

```text
SavingsPlan
    │
    ├── sourceWalletId
    ├── targetWalletId
    │
    ├── minimumRetainedBalance
    │
    └── Rules
         │
         ├── Percentage
         ├── Threshold
         └── RoundUp
```

E o fluxo:

```text
DepositCompletedEvent
        │
        ▼
SavingsEventListener
        │
        ├── validate origin
        │
        ├── load active plans
        │
        ├── evaluate rules deterministically
        │
        └── dispatch TransferFunds
                    │
                    ├── deterministic operation_id
                    ├── origin=SAVINGS_AUTOMATION
                    └── sourceOperationId
                              │
                              ▼
                         Ledger API
                              │
                              ▼
                   Fraud + Idempotency + ACID
```

**Minha leitura é que a SPEC está cerca de 85–90% pronta para ratificação.** A estrutura modular está certa; agora precisamos fechar essas poucas decisões de semântica e concorrência, porque são elas que vão determinar o `PLAN-001` e os contratos de eventos.
