**I would implement 000.9.2 first, then 000.9.3.** There is a good architectural reason for that ordering.

### Why 000.9.2 first

000.9.2 establishes the **runtime topology in which 000.9.3's security actually operates**:

```text
000.9.1
Logical process separation
        │
        ▼
000.9.2
Physical/runtime separation
        │
        ├── Edge container
        ├── Core container
        ├── NATS boundary
        ├── /spool durability
        ├── independent scaling
        ├── lifecycle/shutdown
        └── network topology
        │
        ▼
000.9.3
Security boundary
        │
        ├── TLS 1.3
        ├── HMAC authentication
        ├── credential resolution
        ├── tenant derivation
        ├── tenant rate limiting
        └── Core authorization
```

The important point is that **000.9.3 assumes the Edge/Core boundary already exists physically**.

If we implement 000.9.3 first while everything is still running as a monolith or semi-monolith, we risk implementing security around assumptions that change immediately afterward.

---

## The strongest argument: HMAC belongs at the real Edge

000.9.3 says:

> Edge authenticates cryptographically; Core enforces tenant ownership.

That becomes much cleaner once we actually have:

```text
Internet
   │
   ▼
Edge process
   │
   │ authenticated / verified
   ▼
NATS
   │
   ▼
Core process
```

Then the trust boundary is very explicit:

```text
                 UNTRUSTED
                    │
                    ▼
             ┌──────────────┐
             │     EDGE     │
             │              │
             │ HMAC verify  │
             │ tenant derive│
             │ rate limit   │
             └──────┬───────┘
                    │
              TRUSTED EDGE
                    │
                    ▼
             ┌──────────────┐
             │ NATS / IPC   │
             └──────┬───────┘
                    │
                    ▼
             ┌──────────────┐
             │     CORE     │
             │              │
             │ tenant authz │
             │ DB ownership │
             │ transaction  │
             └──────────────┘
```

That is essentially the security architecture we want.

# There is one exception

I would **not wait until 000.9.3 to put basic transport security into 000.9.2**.

000.9.2 should establish the **TLS/secret injection plumbing**, without implementing the HMAC protocol.

For example:

### 000.9.2

```text
NATS_URL
NATS credentials
TLS certificates
truststore
keystore
secret mounts
```

and:

```text
Edge ──TLS──> NATS
Core ──TLS──> NATS
```

where applicable.

But:

```text
X-Key-Id
X-Timestamp
X-Operation-Id
X-Signature
```

belongs entirely to **000.9.3**.

That avoids mixing deployment mechanics with authentication semantics.

---

# Another important reason: 000.9.2 exposes flaws in 000.9.3

Once we actually run:

```text
Edge-1
Edge-2
Core-1
Core-2
Core-3
NATS
Postgres
Dragonfly
```

we can validate things that matter to 000.9.3:

### Credential resolution

Does every Edge have the same credential snapshot?

```text
CredentialSnapshot v17
       │
 ┌─────┼─────┐
 ▼     ▼     ▼
E1    E2    E3
```

### Rate limiting

000.9.2 establishes independent Edge instances.

Then 000.9.3 can decide whether:

```text
E1 local bucket
E2 local bucket
E3 local bucket
```

is sufficient, or whether the distributed Dragonfly fallback is actually needed.

### Tenant security

The actual:

```text
Edge → NATS → Core
```

deployment allows us to verify that the tenant information crossing the boundary is properly derived and cannot simply be supplied by a client.

# The implementation sequence I'd use

I would make it:

```text
000.9.1
Process separation
        │
        ▼
000.9.2
Container/runtime topology
        │
        ├── Docker Compose
        ├── Edge/Core images
        ├── NATS IPC
        ├── spool volumes
        ├── health
        ├── shutdown
        └── multi-instance
        │
        ▼
000.9.3
Security perimeter
        │
        ├── TLS 1.3
        ├── HMAC-SHA256
        ├── tenant derivation
        ├── rate limiting
        ├── SSE authorization
        └── Core tenant isolation
        │
        ▼
000.10
Financial payload cryptographic protection
        │
        ▼
000.11
DLQ / spillover / replay intelligence
```

There is a nice architectural progression here:

**000.9.1 = separation**
**000.9.2 = deployment**
**000.9.3 = trust**
**000.10 = data protection**
**000.11 = resilience/recovery**

---

## One adjustment I'd make to 000.9.2 because of this ordering

Since **000.9.3 is immediately next**, I'd add a small section to 000.9.2 called something like:

### `5. Security & Secret Injection Boundary`

Only establish the infrastructure contracts:

* TLS 1.3-capable listeners/connections.
* Secret injection through platform-native mechanisms.
* No secrets baked into OCI images.
* No secrets in environment-independent configuration committed to source.
* NATS authentication/TLS configurable externally.
* Edge/Core containers run non-root.
* Network policies/security groups may restrict Core from direct public ingress.
* Core is reachable only through its intended internal interfaces.

**No HMAC implementation here.**

Then 000.9.3 consumes that foundation.

---

### So my recommendation is unequivocal:

**Implement `000.9.2 → 000.9.3`, not the reverse.**

And before starting implementation, I'd revise 000.9.2 with the corrections above—particularly **independent `N/M` scaling, spool durability semantics, shutdown ordering, and the Edge/Core/NATS trust topology**.

After that, **000.9.3 can be implemented against a real multi-process boundary rather than a conceptual one.**
