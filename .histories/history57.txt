Yes. Looking at the revised SPEC, I would **change this part**, but I would *not* replace GitHub Pages with Vercel.

The bigger opportunity is to simplify the architecture by **removing GitHub Pages entirely for Helm distribution**.

Your new SPEC has effectively created three separate concerns:

1. **OCI images** → GHCR
2. **Helm charts** → GitHub Pages / `index.yaml`
3. **Appliance deployment** → Portainer GitOps/webhook

The first and third make sense. The second is now somewhat legacy/duplicated infrastructure. Your current requirement explicitly creates an `gh-pages` Helm repository in `REQ-TOP-017`.

### I'd use GHCR for both images *and* Helm

Modern Helm supports OCI registries natively since Helm 3.8, including `helm push`, `pull`, `install`, dependencies, and immutable digest references. ([Helm][1])

So the pipeline becomes:

```text
GitHub
   │
   ├── GitHub Actions
   │      │
   │      ├── Build/Test
   │      ├── wallet-edge → GHCR
   │      ├── wallet-core → GHCR
   │      └── wallet-platform Helm → GHCR OCI
   │
   └── Portainer
          │
          └── pulls Compose / image versions
```

For example:

```bash
helm package deploy/helm/wallet-platform

helm push wallet-platform-4.0.0.tgz \
  oci://ghcr.io/<owner>/helm
```

Then installation becomes:

```bash
helm install wallet-platform \
  oci://ghcr.io/<owner>/helm/wallet-platform \
  --version 4.0.0
```

And, importantly, Helm supports installing by immutable digest as well, which is useful for your appliance/security direction. ([Helm][1])

GitHub's Container Registry already supports OCI artifacts and is designed around GitHub Actions/GITHUB_TOKEN workflows. ([GitHub Docs][2])

## What about Vercel?

I wouldn't use Vercel **for the Helm repository**.

Vercel is attractive if you want something like:

```text
wallet-platform.dev
├── Documentation
├── Architecture
├── Deployment guide
├── API docs
├── Helm documentation
└── Appliance documentation
```

That's a different problem.

So I'd separate:

| Need                  | Technology I'd use                           |
| --------------------- | -------------------------------------------- |
| Source                | GitHub                                       |
| CI/CD                 | GitHub Actions                               |
| Docker/OCI images     | **GHCR**                                     |
| Helm charts           | **GHCR OCI**                                 |
| Plan B deployment     | Docker Compose + Portainer                   |
| Kubernetes deployment | Helm                                         |
| Documentation website | **Vercel / Cloudflare Pages / GitHub Pages** |
| Runtime               | Edge + Core + NATS                           |
| GitOps trigger        | Portainer                                    |

This is actually **simpler than your current SPEC**.

### The particularly nice part

You eliminate:

```text
gh-pages branch
       ↓
helm-pages.yml
       ↓
index.yaml
       ↓
GitHub Pages HTTP server
       ↓
helm repo add
```

and replace it with:

```text
GitHub Actions
       ↓
GHCR OCI
       ↓
helm install oci://...
```

Helm itself now recommends considering OCI registries when creating a chart repository. ([Helm][3])

### One other thing I'd change

There's a subtle conceptual issue with this line:

> **Plan B appliance MUST support automated redeployment triggered via Portainer Webhook invocation from the CI/CD pipeline and/or Git repository polling.**

I'd make **Git repository polling the fallback**, not an equal primary mechanism.

For your appliance architecture I'd prefer:

```text
GitHub Actions
    │
    ├── build/test
    ├── publish images → GHCR
    ├── publish Helm → GHCR
    │
    └── Portainer webhook
             │
             ▼
       Appliance
             │
             └── pull immutable image
```

The appliance doesn't need to host a Helm repository or become a sophisticated GitOps platform.

That fits very well with your original goal of a **low-cost, appliance-grade deployment**: minimal moving pieces, no Kubernetes tax for Plan B, but still a clean upgrade path to Rancher/GKE.

**So my recommendation is: don't move from GitHub Pages → Vercel. Move from GitHub Pages → GHCR OCI.** Use Vercel/Cloudflare Pages later only if you want a polished public documentation/product site.
