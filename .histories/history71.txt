Yes — and I think treating this as the **first scratch of 000.10** is the right approach. The direction is clear: **000.9.3 established perimeter authentication/trusted identity; 000.10 extends that trust boundary into cryptographic protection of the financial payload and its handling after admission.** The draft explicitly frames that progression.

I would **not move to PLAN/TASKS yet**. There are several architectural points worth resolving while this is still scratch.

### What I think 000.10 should become

The current pillars are coherent:

1. **Envelope encryption**

   * AES-256-GCM
   * DEK per command/batch/session
   * KEK remains inside KMS
   * opaque ciphertext in the Edge journal

2. **Cryptographic replay protection**

   * existing timestamp freshness from 000.9.3
   * additional `X-Nonce`
   * atomic single-use admission through Dragonfly

3. **Telemetry/data leakage protection**

   * logs
   * traces
   * exception messages
   * potentially metrics/tags

4. **Cryptographic key lifecycle**

   * this is currently implicit in the KMS SPI but probably deserves more explicit treatment.

The scratch already establishes the important separation from 000.9.3: HMAC remains authoritative for **authentication/integrity of the ingress request**, while 000.10 protects the **payload as data**.

---

## The biggest things I'd change before ratification

### 1. Don't put decryption "inside the transaction boundary"

This line is the one I'd challenge most:

> `CoreCommandConsumer` MUST unwrap the DEK and decrypt the payload inside the transaction boundary.

That conflicts with the architecture we've established around **no external/cache/KMS blocking while holding the financial DB transaction**.

KMS/Dragonfly/network I/O should ideally be:

```text
NATS message
   │
   ├── authenticate trusted transport
   ├── validate envelope
   ├── nonce/replay check
   ├── unwrap DEK
   ├── decrypt + authenticate GCM
   ├── validate command
   │
   ▼
BEGIN DB TRANSACTION
   │
   ├── tenant/account checks
   ├── ledger mutation
   ├── outbox
   └── COMMIT
```

So I'd change the invariant to something like:

> **Cryptographic authentication MUST complete before the financial transaction begins.**

That gives us a much stronger boundary.

---

### 2. The 000.10 encryption model needs one crucial question answered

**Who encrypts the payload?**

The current draft implies Edge does it, but that needs to become explicit.

Probably:

```text
Client
  │
  │ plaintext HTTPS/HMAC request
  ▼
EDGE
  │
  ├─ authenticate HMAC
  ├─ resolve tenant
  ├─ validate nonce
  ├─ obtain/generate DEK
  ├─ AES-GCM encrypt
  ├─ journal ciphertext
  │
  ▼
NATS
  │
  ▼
CORE
  │
  ├─ unwrap DEK
  ├─ decrypt
  └─ financial transaction
```

But if the client is already sending plaintext over authenticated TLS to Edge, this is not literally **end-to-end encryption**. It is more accurately:

**application-layer encryption between Edge persistence/transport boundaries and Core.**

That terminology matters because "end-to-end" could imply that the plaintext is never visible at Edge.

---

### 3. KMS semantics need much more precision

The current:

```java
generateDataKey(tenantId, keyId)
decryptDataKey(tenantId, keyId, wrappedDek)
```

is a good starting SPI, but there are unanswered questions:

* Is the DEK generated by KMS or locally?
* Does `generateDataKey()` return both plaintext DEK and wrapped DEK?
* Does Core have permission to unwrap?
* Does Edge have permission to unwrap?
* Are Edge and Core using the same KMS credential?
* What exactly does `keyId` identify?
* Can a tenant have multiple active KEKs?
* How does KEK rotation work?
* How are old envelopes decrypted after rotation?
* Is `tenantId` cryptographically bound to the envelope?

I'd strongly consider an envelope containing something like:

```text
version
algorithm
tenantId
keyId
iv
wrappedDek
ciphertext
authTag
```

Although with GCM the tag can be represented as part of ciphertext depending on the encoding.

Most importantly, **tenant binding should be authenticated data (AAD)**.

For example conceptually:

```text
AAD =
    protocolVersion
    tenantId
    operationId
    keyId
    algorithm
```

Then changing the tenant or operation metadata without re-encryption causes GCM authentication failure.

That would connect 000.10 directly to the tenant-security guarantees of 000.9.3.

---

### 4. Nonce needs two different concepts

The draft currently uses:

```text
X-Nonce
```

and calls it cryptographic nonce replay protection.

But there are actually two different nonces:

**A. Protocol replay nonce**

```text
X-Nonce
```

used to ensure:

```text
same authenticated request ≠ accepted twice
```

**B. AES-GCM IV/nonce**

```text
iv
```

used to ensure:

```text
same DEK + same IV ≠ reused
```

These must **not be conflated**.

The draft does have both conceptually, but I would make the distinction explicit in the terminology and invariants.

This is particularly important because **GCM IV reuse under the same key is a cryptographic catastrophe**, while `X-Nonce` is an application-level replay control.

---

### 5. `X-Nonce` should probably be bound to the authenticated operation

The current invariant is:

```text
Count(Admissions(t,N)) <= 1
```

I'd make the security property stronger.

Conceptually:

```text
ReplayKey =
    tenantId
    + principalId
    + nonce
```

or, depending on the intended protocol:

```text
ReplayKey =
    tenantId
    + operationId
    + nonce
```

And the nonce should be validated **after HMAC authentication**, because otherwise an unauthenticated attacker can fill Dragonfly with arbitrary nonce values.

This is another place where 000.9.3 should be explicitly referenced rather than redefined.

---

### 6. The `P99 < 50µs` requirement is too strong as an architectural invariant right now

The draft says:

> encryption and decryption overhead ... `P99 ≤ 50µs` using JDK 27 hardware-accelerated AES-NI.

AES-GCM itself can potentially fit that budget for small payloads, but the **complete operation** includes:

```text
DEK handling
KMS interaction/cache
envelope construction
allocation/copying
AES-GCM
serialization
```

So I wouldn't make `50µs` a universal invariant before benchmarking.

Better separation:

```text
I-ENV-002
AES-GCM primitive overhead target:
P99 <= X µs
```

and:

```text
I-ENV-003
Edge cryptographic processing budget:
P99 <= Y µs
```

Then benchmark the actual implementation.

This is consistent with what we just did in 000.9.4: distinguish **architectural acceptance criteria** from **optimization targets**.

---

### 7. `HTTP 400` for cryptographic failures needs reconsideration

The current requirement says invalid ciphertext / GCM tag / unresolved KEK →:

```text
HTTP 400
```

But these failures occur at different layers.

For example:

| Failure             | Likely semantic                      |
| ------------------- | ------------------------------------ |
| malformed envelope  | invalid request                      |
| invalid GCM tag     | cryptographic integrity failure      |
| unknown key ID      | key-management/configuration failure |
| KMS unavailable     | infrastructure failure               |
| expired/revoked key | key lifecycle failure                |
| replayed nonce      | authentication/replay rejection      |

And Core isn't necessarily returning an HTTP response at all.

I'd define **internal terminal error codes first**, then map them to HTTP/NATS/DLQ semantics.

---

## 8. PII masking is broader than the current requirement

This:

> account IDs except first 4/last 4, personal identifiers, amounts masked

is a good start, but I'd avoid defining masking as only a formatter.

The stronger invariant should be:

```text
Sensitive data MUST NOT enter telemetry
```

rather than:

```text
Sensitive data enters telemetry and a filter masks it.
```

Because filters can be bypassed through:

* exception messages
* `toString()`
* MDC
* structured logging fields
* NATS diagnostics
* SQL logging
* HTTP access logs
* Netty debug logs
* tracing attributes
* baggage
* metrics labels
* DLQ diagnostic metadata

So I would make **"do not emit" the primary rule**, with masking as a defense-in-depth mechanism.

The draft already points toward this with `Telemetry(req) ∩ SensitiveFields(req) = ∅`.

---

# One architectural addition I'd strongly recommend

### Cryptographic domain separation

I'd like 000.10 to explicitly define different cryptographic purposes.

For example:

```text
WALLET-ENV-V1
WALLET-HMAC-V1
WALLET-LEDGER-HASH-V1
WALLET-NONCE-V1
```

This prevents accidental reuse of keys/material between protocols.

It also gives us a clean evolution path:

```text
SPEC-000.9.3
   │
   └── Authentication / request integrity
        WALLET-HMAC-V1

SPEC-000.10
   │
   ├── Payload confidentiality/integrity
   │     WALLET-ENV-V1
   │
   ├── Replay protection
   │     WALLET-NONCE-V1
   │
   └── Ledger integrity
         WALLET-LEDGER-HASH-V1
```

That makes the security architecture much easier to audit.

## Proposed 000.10 boundary

I would therefore evolve the scratch toward this model:

```text
                    ┌─────────────────────┐
                    │      CLIENT         │
                    └──────────┬──────────┘
                               │
                         TLS + HMAC
                               │
                               ▼
                    ┌─────────────────────┐
                    │        EDGE         │
                    │                     │
                    │  HMAC authenticate  │
                    │  tenant resolution  │
                    │  replay nonce       │
                    │  encrypt payload    │
                    │  telemetry scrub    │
                    └──────────┬──────────┘
                               │
                        opaque envelope
                               │
                         NATS / spool
                               │
                               ▼
                    ┌─────────────────────┐
                    │        CORE         │
                    │                     │
                    │  decrypt/auth GCM   │
                    │  validate command   │
                    │        │            │
                    │        ▼            │
                    │  BEGIN TX           │
                    │  ledger mutation    │
                    │  outbox             │
                    │  COMMIT             │
                    └─────────────────────┘
```

With KMS outside the financial transaction:

```text
          ┌───────────────┐
          │      KMS      │
          │      KEK      │
          └───────┬───────┘
                  │
        wrap / unwrap DEK
                  │
       ┌──────────┴──────────┐
       │                     │
      EDGE                  CORE
```

And Dragonfly:

```text
Dragonfly
   │
   ├── nonce replay state
   ├── velocity/risk state
   └── other non-authoritative hot state
```

with **no financial authority transferred to either KMS or Dragonfly**.

### My current assessment

The scratch has the right **security direction**, and it fits very naturally after 000.9.3. The main thing I'd do now is **tighten the security model before adding more requirements**, particularly:

1. **Edge vs Core encryption responsibilities**
2. **"end-to-end" terminology**
3. **KMS trust/permissions**
4. **DEK/KEK lifecycle and rotation**
5. **GCM IV vs `X-Nonce` distinction**
6. **AAD binding to tenant/operation**
7. **decrypt-before-transaction**
8. **replay-key semantics**
9. **cryptographic vs infrastructure failure taxonomy**
10. **separating measurable performance targets from hard invariants**
11. **telemetry non-emission vs masking**
12. **cryptographic domain separation**

The current scope/non-goals are otherwise nicely constrained: it explicitly avoids turning 000.10 into full DB column encryption or asymmetric client authentication.

**I would keep this as Scratch and make these architectural decisions first.** Then we can produce a clean **SPEC-000.10 Rev.1** before creating ARCH/PLAN/TASKS.
