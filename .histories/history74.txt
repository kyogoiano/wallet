This Rev. 2 is **substantially better** than the previous plan. The separation between the security contracts and infrastructure adapters, the immutable envelope, sealed replay algebra, pre-transaction cryptographic gate, and dual Gradle/Modulith boundary are all coherent.

However, I would **not mark it TASK-ready yet**. I see **5 MUST-level corrections**, plus several SHOULD refinements. The most important ones are around **DEK lifecycle, nonce admission, KMS binding, and the “contracts only” boundary**.

# 2. MUST #1 — Fix nonce admission semantics

This is the biggest issue I found.

Your sequence is:

```text
HMAC
  ↓
NonceTracker.admit()
  ↓
Accepted
  ↓
KMS / DEK
  ↓
AES-GCM
  ↓
Journal
  ↓
NATS
```

Suppose:

```text
Nonce = N123
HMAC = valid
NonceTracker = Accepted
KMS = timeout
```

The client retries the **same legitimate request**.

Now:

```text
Nonce N123 already exists
        ↓
Rejected / replay
        ↓
401
```

You've converted a transient internal failure into a permanent client-visible replay rejection.

The same happens if:

* encryption fails;
* journal append fails;
* journal fsync fails;
* NATS publication fails after journal persistence;
* Edge crashes between nonce admission and durable acceptance.

That is particularly problematic because your existing architecture deliberately distinguishes **security replay protection** from **financial idempotency**.

### I would change the model

Don't model nonce admission as merely:

```java
Accepted
Rejected
Unavailable
```

Instead, make the lifecycle explicit.

For example:

```text
NonceReservation
 ├── Accepted
 ├── Rejected
 └── Unavailable
```

with an explicit relationship to durable acceptance.

Conceptually:

```text
HMAC
  ↓
reserve nonce
  ↓
encrypt
  ↓
durable journal append
  ↓
commit nonce admission
```

Or, if you deliberately want the nonce to be consumed immediately, then the specification must explicitly state:

> Once nonce admission succeeds, all subsequent Edge failures are retriable only through `Idempotency-Key`/operation state and MUST NOT require reuse of the same nonce.

But that requires an additional mechanism because the current Edge has no relational source of truth.

### Required test

Add:

`NonceAdmissionFailureRecoveryTest`

Cases:

1. nonce accepted → KMS failure → retry same request
2. nonce accepted → journal failure → retry
3. nonce accepted → Edge crash before durable journal
4. nonce accepted → successful journal → duplicate retry
5. concurrent same nonce

This is a **MUST fix**.

# 3. MUST #2 — DEK cache semantics need redesign

The phrase:

> “Evicts after 100,000 encryptions.”

is problematic.

A cache doesn't naturally have an eviction policy based on the number of encryptions unless you explicitly implement an encryption-use counter.

More importantly, the current plan doesn't clearly define **what the cache key is**.

You currently have:

```text
CachedKeyManagementClient
    ↓
plaintext DEK
```

but we need something like:

```text
CacheKey = (tenantId, keyId, wrappedDek identity)
```

or, if the design intends to reuse one generated DEK:

```text
CacheKey = (tenantId, keyId)
CachedValue = plaintext DEK + wrapped DEK + creation metadata
```

Those are materially different security models.

### Why this matters

AWS KMS's data-key model supports exactly the general pattern you're using: a plaintext data key is returned for immediate encryption and an encrypted copy can accompany the ciphertext. AWS explicitly recommends erasing the plaintext key after use. ([AWS Documentation][1])

Your cache deliberately extends plaintext DEK lifetime, so that extension needs to be an explicit architectural decision.

I'd define:

```text
DEK Cache Entry
----------------
tenantId
keyId
wrappedDek
SensitiveKeyMaterial plaintextDek
createdAt
expiresAt
encryptionCount
```

and explicitly specify:

```text
maxAge = 10 min
maxUses = N
maxEntries = M
```

rather than:

> “evicts after 100,000 encryptions”

Also specify:

* whether `maxUses` is per DEK;
* whether cache entries are tenant-isolated;
* whether concurrent callers can exceed `maxUses`;
* whether eviction waits for in-flight encryption;
* whether plaintext DEK is zeroized immediately after eviction;
* whether rotation invalidates the cache;
* whether a KMS-generated wrapped DEK is reused across envelopes.

### Important point

**100,000 encryptions per DEK is not automatically wrong**, but it needs to be justified against the GCM invocation budget and key lifecycle.

NIST explicitly imposes an invocation/IV uniqueness constraint for GCM and discusses global invocation limits under a given key. ([NIST Publications][2])

So I'd make the limit a cryptographic policy, not merely a cache-performance number.

# 4. MUST #3 — Bind the wrapped DEK to the tenant

This is the security improvement I would definitely add.

Your application-level AAD is:

```text
version
tenantId
operationId
keyId
algorithm
```

That's good.

But your **KMS-wrapped DEK** is a separate cryptographic object.

The architecture should bind:

```text
wrapped DEK
    ↕
tenant
    ↕
KMS key
```

Otherwise the wrapped DEK is cryptographically valid independently of the envelope's AAD.

For AWS KMS specifically, an **Encryption Context** is authenticated additional data and must match during decrypt; AWS recommends it for this use. ([AWS Documentation][1])

I would therefore introduce something conceptually like:

```text
KMS Encryption Context

WALLET-ENV-V1
tenant_id = <tenant>
key_domain = WALLET-ENV-V1
```

Possibly:

```text
key_id = <key-id>
```

if the provider semantics support it appropriately.

I would **not put `operationId` into the KMS encryption context if the wrapped DEK is reused across multiple envelopes**, because then every envelope would require a different wrapped DEK.

Instead:

```text
KMS binding:
    tenantId
    key domain/version

GCM AAD:
    tenantId
    operationId
    envelope version
    keyId
    algorithm
```

This gives you two independent bindings.

### Result

```text
             KMS protection
                 │
       tenant ───┤
                 ↓
             wrapped DEK
                 │
                 ↓
       plaintext DEK
                 │
                 ↓
       AES-256-GCM
                 │
       ┌─────────┴─────────┐
       ↓                   ↓
   plaintext             AAD
                         tenant
                         operation
                         version
                         keyId
                         algorithm
```

That's considerably stronger.

# 6. MUST #5 — Strengthen the CryptoEnvelope validation

This is already quite good:

```java
if (iv.length() != 12)
```

But the envelope should validate more than that.

At minimum:

```text
version supported
algorithm supported
IV = 12 bytes
wrappedDek != empty
ciphertext >= authentication-tag length
tenantId valid
operationId valid
keyId valid
```

Also explicitly define:

```text
GCM tag = 128 bits
AES key = 256 bits
IV = 96 bits
```

The 96-bit IV is consistent with standard GCM practice, and NIST's GCM guidance treats IV uniqueness as a critical security requirement. ([NIST Publications][3])

I'd also make the IV generation contract explicit:

```java
GcmIv generate();
```

backed by:

```java
SecureRandom
```

rather than leaving “CSPRNG” as an implementation assumption.

# 7. AAD implementation: good, but one change

The move from delimiter-based strings to length-prefixed encoding is **exactly the right direction**.

This:

```text
tenant|operation|key
```

was vulnerable to canonicalization ambiguity.

This:

```text
[length][value]
[length][value]
...
```

is much better.

However, I would change:

```java
buffer.putShort((short) bytes.length);
```

to an explicitly bounded encoding.

For example:

```text
uint32 length
```

plus:

```text
MAX_FIELD_LENGTH
```

Otherwise:

```java
(short) bytes.length
```

has an implicit signed 16-bit limit and can produce undesirable behavior for oversized values.

Even better, don't allocate:

```java
ByteBuffer.allocate(256)
```

with a guessed size.

Define the canonical format first, calculate the exact size, then serialize.

### Add

```text
CanonicalAadGoldenVectorTest
```

with known hexadecimal inputs/outputs.

For crypto protocols, a golden vector is much more valuable than simply asserting:

```java
aad1.equals(aad2)
```

# 8. One subtle issue: `CryptoEnvelope` doesn't need IV in AAD

I **would not** add IV to your AAD merely because it is an envelope field.

GCM's IV is already an authenticated input to the GCM operation; NIST describes authentication as covering the plaintext, AAD, IV and tag. ([NIST Publications][2])

So your current separation is reasonable:

```text
GCM IV
    → GCM authenticated input

AAD
    → semantic envelope binding
```

That's cleaner than redundantly including the IV in the AAD.

# 10. `GeneratedDataKey` has a lifecycle problem

This:

```java
public record GeneratedDataKey(
    SensitiveKeyMaterial plaintextDek,
    CryptoBytes wrappedDek
) {}
```

is okay structurally, but it doesn't enforce lifecycle.

I'd strongly consider:

```java
public final class GeneratedDataKey implements AutoCloseable {
    private final SensitiveKeyMaterial plaintextDek;
    private final CryptoBytes wrappedDek;

    ...
}
```

so the intended usage becomes:

```java
try (GeneratedDataKey key = kms.generateDataKey(...)) {
    encrypt(key.plaintextDek());
}
```

This makes the secure lifecycle visible in the API.

And your own `SensitiveKeyMaterial` approach is good:

```java
try {
    ...
} finally {
    close();
}
```

But be precise in the spec: Java array zeroization is a **best-effort memory hygiene mechanism**, not a guarantee that every JVM copy has disappeared.

## Final assessment

**This is a strong Rev. 2 and much closer to the architecture we want.** The most important conceptual improvement is that you have now separated:

```text
authentication
≠
replay protection
≠
payload confidentiality
≠
cryptographic integrity
≠
financial transaction authorization
```

That's exactly the right decomposition.

The remaining concern isn't that the cryptographic primitives are wrong; it's that **the lifecycle around them isn't completely specified yet**—especially nonce consumption and plaintext DEK reuse.

I would therefore change the header from:

> 🟢 Approved (Rev. 2)

to:

> 🟡 **Architecture Review Passed — Rev. 2.1 Required Before TASK Generation**

Once those five MUST areas are incorporated, I would be comfortable moving directly into **TASKS-000.10** with the security skill governing the implementation.

The external cryptographic references also support the two most important design principles here: GCM IV uniqueness must be controlled across invocations under a key, and KMS encryption context can bind a wrapped data key to non-secret context such as tenant identity. ([NIST Publications][2])
