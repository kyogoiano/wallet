## 1. O maior ponto: `TASK-1.4` mistura regras de eventos diferentes

Hoje:

```text
Percentage → Threshold → Round-Up
```

como ordem global.

Mas, conceitualmente:

```text
DepositCompletedEvent
        │
        ├── Percentage
        └── Threshold

TransferCompletedEvent
        │
        └── Round-Up
```

Portanto, eu não modelaria o engine como:

```java

```

com uma ordem:

```text
Percentage → Threshold → Round-Up
```

para todos os eventos.

Eu definiria:

### Deposit flow

```text
Percentage → Threshold
```

### Transfer flow

```text
Round-Up
```

Então ajustaria o `TASK-1.4` para:

> Deterministic evaluation order SHALL be event-specific:
>
> * `DepositCompletedEvent`: Percentage → Threshold
> * `TransferCompletedEvent`: Round-Up only

Isso evita um `SavingsRuleEngine` excessivamente genérico e cheio de `if`.

# 3. O algoritmo de `TASK-1.4` precisa considerar o refresh após Percentage

Este é um ponto sutil.

Se temos:

```text
Balance = 10,000
Percentage = 10%
Threshold = 8,000
```

O Percentage calcula:

```text
Sweep = 1,000
```

Mas, depois que esse sweep é executado, o Threshold não deveria continuar assumindo:

```text
Balance = 10,000
```

senão:

```text
Percentage → 1,000
Threshold → 2,000
```

resultaria em:

```text
Total = 3,000
```

quando o saldo após Percentage seria `9,000`.

Por isso precisamos definir onde acontece a composição.

Minha recomendação:

### O Rule Engine calcula intenções, não executa

```text
Current Balance
      │
      ▼
Percentage Calculation
      │
      ▼
Projected Balance
      │
      ▼
Threshold Calculation
```

Exemplo:

```text
Initial balance = 10,000
Min retained = 0

Percentage sweep = 1,000
Projected balance = 9,000

Threshold = 8,000
Threshold sweep = 1,000

Total intended sweep = 2,000
```

Ou seja:

```java
projectedBalance =
    currentBalance.subtract(percentageSweep);

thresholdSweep =
    thresholdCalculator.calculate(
        projectedBalance,
        threshold
    );
```

Isso mantém o cálculo determinístico sem exigir que o Savings execute uma transferência antes de calcular a próxima.

Eu deixaria isso explícito no `TASK-1.4`.

# 4. Atenção: uma única transferência ou várias?

Depois do item acima, precisamos decidir.

Se Percentage e Threshold produzem:

```text
Percentage = R$ 1.000
Threshold  = R$ 1.000
```

fazemos:

### Opção A

```text
Transfer 1 → R$ 1.000
Transfer 2 → R$ 1.000
```

### Opção B

```text
Transfer → R$ 2.000
```

Para V1, eu escolheria **Opção A**.

Porque cada regra possui:

```text
ruleId
sourceOperationId
deterministic operationId
execution history
```

Então:

```text
sourceOp + ruleA
```

é uma execução.

```text
sourceOp + ruleB
```

é outra.

Isso melhora:

* auditabilidade;
* idempotência;
* métricas por regra;
* debugging;
* retries independentes.

# 5. `TASK-1.6`: cuidado com `InsufficientFundsException`

Concordo que:

```text
InsufficientFundsException
FraudBlockedException
```

devem ser tratadas.

Mas eu não colocaria essas duas classes diretamente como a única estratégia.

O ideal seria classificar o resultado:

```java
public enum SavingsExecutionStatus {

    EXECUTED,

    SKIPPED_INSUFFICIENT_FUNDS,

    REJECTED_BY_FRAUD,

    FAILED_RETRYABLE,

    FAILED_PERMANENT
}
```

Então o serviço:

```text
TransferFundsUseCase
       │
       ├── success
       │      ↓
       │   EXECUTED
       │
       ├── known business rejection
       │      ↓
       │   SKIPPED / REJECTED
       │
       └── infrastructure failure
              ↓
          retryable?
```

Isso vai casar muito bem com a `savings_execution_history`.

Eu adicionaria isso ao `TASK-1.6`.

Eu colocaria isso no:

## Minha conclusão

O `TASKS-001` está **bom o suficiente para começar**, mas eu faria esses ajustes antes:

### Obrigatórios

1. separar a ordem das regras por tipo de evento;
2. testar propagação real de `OperationOrigin`;
3. definir a semântica do saldo projetado entre Percentage e Threshold;
4. definir o lifecycle/status da `SavingsExecution`;
5. adicionar unicidade/deduplicação em `SavingsExecutionHistory`;
6. criar o boundary Modulith logo no início.

### Opcionais, mas recomendados

7. dividir `SavingsPlanService` e `SavingsQueryService` em tasks separadas;
8. usar duas transferências independentes quando múltiplas regras forem aplicáveis.
