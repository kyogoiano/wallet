Sim. Esta Rev.2 está **bem melhor** que a anterior, principalmente porque agora a 000.12 já declara explicitamente que DLQ/retry não é responsabilidade dela. Mas, olhando como SPEC que vai virar PLAN/TASKS, eu ainda faria alguns ajustes antes de ratificar.

O ponto principal é que agora temos **duas responsabilidades bem delimitadas**:

```text
SPEC-000.11
Edge ──NATS──> Core
        │
        └── retry / DLQ / replay / ACK


SPEC-000.12
Core
 ├── command consumers
 ├── ledger
 ├── fraud
 └── savings
       │
       └── Modulith events
```

A 000.12 já explicita corretamente que o Core é um único processo e que NATS representa a fronteira interprocesso.

## 1. O maior problema restante: `dlq` ainda está no Bound Context

No cabeçalho:

> `Spring Modulith DAG (ledger, fraud, savings, dlq) & :edge`

Mas a própria SPEC diz:

> DLQ, failure classification e retry são governados pela 000.11.

Então eu **tiraria `dlq` do bounded context/module da 000.12**, a menos que exista realmente um módulo Spring Modulith `dlq` que tenha responsabilidades além da reprocessing infrastructure.

Eu deixaria:

```text
Bounded Context / Module:
Spring Modulith DAG (ledger, fraud, savings) & :edge
```

E, se o projeto realmente possui infraestrutura `dlq`, trataria como:

```text
shared infrastructure / reprocessing infrastructure
```

e não como capability de negócio.

Isso evita uma ambiguidade perigosa:

```text
000.11 → DLQ
000.12 → módulo dlq
```

que pode fazer o Antigravity novamente colocar lógica de DLQ dentro da 000.12.

# 2. `I-STREAM-006` está correto, mas a referência está errada

Hoje:

> `SPEC-000.11 (I-TDLQ-009)`

Precisamos tomar cuidado aqui.

Na definição que estabelecemos para 000.11, **durable handoff antes do ACK** é uma propriedade arquitetural da reprocessing pipeline. Se o ID oficial na 000.11 não for exatamente `I-TDLQ-009`, essa referência vai quebrar a rastreabilidade.

Eu faria uma referência mais robusta:

```text
I-STREAM-006:
Ingress command consumers MUST obey the durable-handoff-before-ACK
contract defined by SPEC-000.11.
```

Sem acoplar a um ID interno da outra SPEC.

Ou, se quisermos máxima rastreabilidade:

```text
I-STREAM-006:
Ingress command consumers MUST satisfy
SPEC-000.11:I-TDLQ-XXX.
```

Mas só depois de congelarmos o ID da 000.11.

# 3. `I-STREAM-001` precisa ser ligeiramente mais preciso

Hoje:

> Internal state projections and reactions ... MUST communicate via in-process `@ApplicationModuleListener`.

Isso é bom, mas pode ficar excessivamente absoluto.

Temos três tipos diferentes de comunicação dentro do Core:

```text
command → use case
domain event → listener
module API → direct invocation
```

Nem toda comunicação entre módulos deve obrigatoriamente ser evento.

Eu escreveria:

```text
I-STREAM-001 — Intra-Core Event Transport

Domain events emitted within Wallet Core MUST be delivered to
interested Wallet Core modules through Spring Modulith in-process
events (`@ApplicationModuleListener`).

Such events MUST NOT be serialized, published to external NATS,
and consumed again by another module in the same JVM.
```

Isso é mais correto arquiteturalmente.

Porque:

```text
fraud → ledgerService.somePublicOperation()
```

não precisa virar evento simplesmente porque são módulos diferentes.

# 4. O `@ApplicationModuleListener` não deveria necessariamente ser "transactional async"

Na tabela você colocou:

> `I-STREAM-001 (@ApplicationModuleListener transactional async)`

Eu removeria **async** dessa frase.

Porque existe uma decisão arquitetural importante aqui:

```text
@TransactionalEventListener
```

versus

```text
@ApplicationModuleListener
```

e ainda:

```text
async
```

pode alterar:

* ordering;
* transaction boundary;
* error propagation;
* retry;
* consistency;
* observability.

A SPEC não precisa decidir isso se o requisito real é simplesmente:

> **não usar NATS para eventos intra-Core.**

Eu deixaria:

```text
I-STREAM-001
...
through Spring Modulith in-process events.
```

E a escolha:

```text
sync vs async
transactional vs non-transactional
```

vai para ARCH/PLAN conforme o caso de uso.

# 5. `I-STREAM-002` está bom, mas "message consumer classes" é amplo

Hoje:

```text
Message consumer classes MUST reside inside <module>.internal.messaging
```

Mas no Pillar B temos:

```text
fraud.internal.listener.FraudGraphListener
```

Ou seja, a própria SPEC usa dois conceitos:

```text
internal.messaging
internal.listener
```

Eu não forçaria tudo para `internal.messaging`.

Melhor:

```text
I-STREAM-002 — Modulith Ownership & Encapsulation

Inbound adapters and event listeners MUST reside inside the

module API.

They MAY be organized under `internal.messaging`,
`internal.listener`, or another capability-specific internal
subpackage.
```

Assim a arquitetura fica coerente com o código real.

# 8. `I-STREAM-008` está correto, mas precisa considerar migration

Perfeito.

Mas durante rollout podemos ter:

Se existir consumer antigo e novo simultaneamente, temporariamente teremos dois possíveis consumidores.

Então eu acrescentaria:

Isso evita o clássico:

# 12. Pillar B precisa preservar semântica transacional

Aqui existe um ponto que merece ser explicitado.

Hoje:

```text

   │
   ├── ledger commit
   │
   └── TransferCompletedEvent
          │
          └── FraudGraphListener
```

Precisamos decidir se:

```text
FraudGraphListener
```

é:

ou:

ou:

A SPEC atual não define isso.

Eu colocaria um requisito:

```text
For each migrated Modulith event listener, the implementation
MUST preserve the existing transactional and consistency
semantics of the event flow unless an explicit architecture
decision approves a change.
```

Isso é muito importante numa refatoração "pure refactor".

# 13. "Pure Refactor" precisa ser uma invariância explícita

Esse é provavelmente o maior reforço que eu faria.

Se o título diz:

> Pure Refactor

então precisamos provar que o comportamento não mudou.

Adicionar:

### `I-STREAM-010 — Behavioral Preservation`

```text
The migration MUST preserve the externally observable business
semantics of the existing command and event flows, including:

- command identity;
- tenant context;
- authorization/security context;
- transaction boundaries;
- idempotency;
- operation status;
- failure classification;
- durable handoff semantics;
- event payload semantics.
```

E eu colocaria isso como **MUST**.

Porque estamos mexendo em:

```text

       ↓
TransferCommandConsumer
DepositCommandConsumer
WithdrawCommandConsumer
```

e:

```text
NATS
 ↓
Modulith
```

Isso não pode virar uma oportunidade silenciosa para alterar comportamento.

## Veredito

**Eu considero a Rev.2 conceitualmente correta e muito próxima de READY**, mas ainda faria esses ajustes antes de gerar PLAN/TASKS.

Os **4 que eu considero MUST antes de fechar a SPEC** são:

1. **remover `dlq` do bounded-context/module da 000.12**;
2. **formalizar `Behavioral Preservation`**, porque é uma refatoração pura;
3. **definir explicitamente que 000.11 é a autoridade para durable handoff/retry/DLQ**, sem duplicar semântica;
4. **separar claramente Modulith event transport de sync/async/transactional semantics**, deixando a decisão de implementação para ARCH/PLAN.

Com isso, a fronteira fica muito elegante:

> **000.11 garante que uma mensagem Edge → Core não seja perdida e possa ser reprocessada. 000.12 define como o Core organiza seus consumidores e como seus módulos internos se comunicam.**

E isso também resolve a sobreposição que tínhamos identificado anteriormente entre `CORE_COMMAND` e `BOUNDED_CONTEXT`.
