# 2. `REQ-INTEL-001` está permissivo demais

Hoje:

```text
allowed dependencies:
ledger::api,
core::api,
core,
goals::api
```

O problema é:

```text
core
```

Isso potencialmente permite que Intelligence dependa de **qualquer coisa exposta pelo módulo Core**, inclusive APIs que deveriam estar fora dessa fronteira.

Isso contradiz parcialmente o próprio:

> `I-INTEL-004`: MUST NOT depend on ledger internal persistence entities, repositories, transaction managers, or internal services.

E, principalmente, a intenção de transformar Intelligence em bounded context isolado.

Eu mudaria para algo mais restritivo:

```text
REQ-INTEL-001 [MUST]:

Define br.com.wallet.intelligence as a Spring Modulith module
with dependencies restricted to stable public contracts:

- ledger::api
- core::api
- goals::api

No dependency on the root `core` module is permitted unless
the referenced type is explicitly exposed through an approved
public API package.
```

Ou, melhor ainda, **removeria `core` completamente**, se a implementação real não precisar dele.

### Minha preferência

```text
allowedDependencies = {
    "ledger::api",
    "core::api",
    "goals::api"
}
```

Isso deixa a arquitetura muito mais forte.

# 3. `I-INTEL-008`: escolher `eventId` ou `operationId`

Aqui temos uma pequena inconsistência:

> canonical event identity (`operationId` / `eventId`)

Mas o requisito seguinte diz:

> deduplication based on `operationId`

Isso precisa ser resolvido.

Pelas decisões da `SPEC-000.12`, nós já estabelecemos uma distinção importante:

```text
eventId     = identidade do evento
operationId = identidade da operação financeira
```

Portanto eu **não chamaria os dois de canonical event identity**.

Eu faria:

```text
I-INTEL-008 — Idempotent Event Processing

Intelligence event consumers MUST be idempotent with respect
to the canonical `eventId`.

Where domain semantics require command-level deduplication,
`operationId` MAY additionally be used as a business identity.
```

Isso segue melhor a arquitetura que já definimos para eventos Modulith.

### E isso muda o REQ-INTEL-004

Hoje:

```text
canonical event deduplication based on operationId
```

Eu mudaria para:

```text
REQ-INTEL-004 [MUST]:
Implement idempotent event processing based on canonical `eventId`.
Where recurrence/subscription semantics require financial-operation
deduplication, `operationId` MUST be included in the domain identity
used by the relevant projection.
```

Isso é muito mais correto.

# 4. Cuidado com "guarantee idempotent listener execution"

A frase:

> guarantee idempotent listener execution under at-least-once redelivery

é forte demais.

Idempotência não significa que o listener será executado apenas uma vez.

O modelo é:

```text
event delivered
      ↓
listener executes
      ↓
persist
      ↓
event delivered again
      ↓
listener executes again
      ↓
same eventId detected
      ↓
no duplicate side effect
```

Então eu usaria:

> **guarantee idempotent side effects under at-least-once redelivery**

Isso é tecnicamente mais preciso.

# 5. `I-INTEL-003` ficou muito melhor

A correção de:

```text
monetary scale = 2
```

versus:

```text
statistical intermediate precision
```

foi excelente.

Mas eu faria uma pequena melhoria:

> `minimum 6 decimal places intermediate precision`

Isso ainda pode ser interpretado como "o cálculo tem exatamente 6 casas".

Eu escreveria:

```text
Statistical calculations MUST use BigDecimal with sufficient
declared intermediate precision and MUST NOT use binary floating
point. Rounding MUST occur only at explicitly defined persistence,
API, or comparison boundaries.
```

E, se vocês realmente quiserem uma política de 6 casas, aí sim:

```text
minimum 6 decimal places
```

como parâmetro explícito da política.

Porque para CV/confidence podemos querer mais precisão internamente.

# 6. `I-INTEL-005` está correto, mas falta ONNX

Hoje:

```text
{LLM, SLM, Ollama, SpringAI}
```

Isso está correto para **generative/remote semantic inference**, mas o próprio histórico da arquitetura diz que ONNX pode participar do hot path de Fraud.

Portanto não devemos criar uma regra dizendo implicitamente:

> ONNX é proibido no synchronous path.

Não é.

A regra correta é:

```text
Generative models, remote LLM APIs and SLM inference engines
MUST NEVER execute on the financial transaction write path.
```

Isso permite:

```text
Fraud hot path
    ↓
ONNX
```

sem violar 003.

E, separadamente:

```text
Intelligence semantic evaluator
    ↓
ONNX
```

continua sendo nearline.

Ou seja: **o problema não é a tecnologia; é o caminho arquitetural em que ela é usada.**

# 7. `I-INTEL-006` deveria mencionar RuleEvaluator

A arquitetura agora introduziu:

```text
RuleEvaluator
OnnxSubscriptionEvaluator
OllamaSubscriptionEvaluator
```

Isso foi uma ótima melhoria.

Mas então:

> "When semantic evaluators (ONNX/Ollama) are unavailable..."

deveria ser:

```text
When an optional semantic evaluator is unavailable...
```

Porque o `RuleSubscriptionEvaluator` pode continuar disponível.

Mais importante ainda: talvez tenhamos:

```text
RuleEvaluator
      ↓
DecisionAnswer(SUBSCRIPTION)
```

e:

```text
ONNX/Ollama
      ↓
DecisionAnswer(...)
```

Nesse caso, `DecisionUnavailable` só representa indisponibilidade de **um evaluator**, não necessariamente indisponibilidade do **semantic classification capability**.

Isso combina muito melhor com o provider-neutral SPI da 000.8.1, que foi desenhado justamente para permitir diferentes evaluators.

# 8. Mas existe uma questão importante sobre o `RuleSubscriptionEvaluator`

Eu manteria o `RuleSubscriptionEvaluator` como **optional semantic enrichment**, mas não deixaria ele virar uma segunda versão do Pattern Engine.

Precisamos preservar:

```text
Pillar 1
"Existe uma recorrência?"
```

versus:

```text
Pillar 2
"O que é essa recorrência?"
```

O RuleEvaluator poderia fazer algo simples como:

```text
merchant = "Netflix"
    → SUBSCRIPTION
```

ou:

```text
merchant/category known
    → UTILITY
```

Mas ele **não deve reimplementar**:

* cadence
* CV
* cycle detection
* price spike
* lifecycle

Isso continua exclusivamente em 003.1.

# 15. Minha lista final de mudanças

Eu considero a SPEC praticamente **Ready**, mas faria estes ajustes:

### 🔴 MUST

**1. Remover `core` de `allowedDependencies`**, salvo se houver uma API pública explicitamente aprovada.

**2. Corrigir `eventId` vs `operationId`:**

```text
eventId = event identity
operationId = financial operation identity
```

**3. Alterar "idempotent listener execution" para "idempotent side effects".**

**4. Não colocar `subscriptions` como schema ownership da macro 003**, se 003.1 será dona da tabela.

**5. Remover `CashflowForecastDao`/forecast-specific topology da foundation**, deixando 003.2 ser dona.

---

### 🟡 SHOULD

**6. Ajustar `I-INTEL-006` para "optional semantic evaluator".**

**7. Explicitar que `RuleEvaluator` não pode reimplementar a detecção determinística de 003.1.**

**8. Clarificar que a topology é apenas module foundation.**

**9. Refinar precision policy para "minimum declared intermediate precision".**

**10. Adicionar explicitamente no acceptance o zero acesso a persistence internals do Ledger.**
