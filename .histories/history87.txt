# 1. 🔴 `I-INTEL-010` aparece no PLAN, mas não está na Rev do SPEC

Este é o problema de traceability mais objetivo.

O PLAN usa:

```text
I-INTEL-010
```

em:

* ADR-003.3
* `REQ-INTEL-005`
* `REQ-INTEL-006`
* traceability matrix

Mas na Rev do SPEC que revisamos, os invariants estavam:

```text
I-INTEL-001
...
I-INTEL-009
```

Não havia `I-INTEL-010`.

Então temos uma regra importante do nosso SDD:

> **PLAN não pode criar um invariant que não existe no SPEC ratificado.**

### Correção

Se a intenção é manter a regra de multi-tenancy como invariant próprio, devemos promovê-la explicitamente no `SPEC-003`:

```text
I-INTEL-010 — Tenant Isolation

All intelligence domain models, events, persistence keys and analytical
state MUST be explicitly tenant-scoped. Cross-tenant aggregation,
lookup or persistence MUST be impossible by construction.
```

Mas eu **não criaria isso no PLAN**.

Alternativamente, se a Rev já considera essa regra coberta por `I-INTEL-004`, `I-SDD-007` e os contratos existentes, então o PLAN deve simplesmente remover `I-INTEL-010`.

**Minha preferência:** adicionar `I-INTEL-010` ao SPEC, porque tenant isolation é importante demais para ficar implícito.

# 6. 🟡 Idempotency: `eventId + operationId` precisa ficar mais preciso

O PLAN diz:

> `Canonical Event Idempotency Guard (eventId + operationId)`

Isso ainda pode induzir uma implementação errada.

A regra que estabelecemos é:

```text
eventId = identity of the event
operationId = identity of the financial operation
```

Logo:

### Redelivery protection

deve ser:

```text
eventId
```

### Business-level deduplication

pode usar:

```text
operationId
```

dependendo da capacidade.

Eu mudaria para:

```text
Canonical Event Idempotency Guard
(eventId)
```

e documentaria:

```text
operationId MAY be used for domain-level deduplication
where business semantics require it.
```

Isso evita alguém implementando uma chave:

```text
(eventId, operationId)
```

como se os dois fossem necessários para identificar o evento.
