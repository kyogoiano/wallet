## 1. 🔴 `TASK-3.1.9` precisa definir a origem do `WithdrawCompletedEvent`

Este é o principal ponto que ainda ficou parcialmente aberto.

A task diz:

> `WithdrawCompletedEvent without resolvable external counterparty is discarded`

Isso é correto, mas não define **como** determinar o `counterpartyId` quando ele existe.

Para `TransferCompletedEvent`, temos:

```text
walletId       = from
counterpartyId = to
```

Para `WithdrawCompletedEvent`, o TASKS deveria exigir explicitamente que o listener use o **campo/contrato canônico existente** do evento, e não faça parsing de descriptor, nome, texto etc.

Eu mudaria a task para algo conceitualmente assim:

```text
WithdrawCompletedEvent MUST enter clustering only when its canonical
external counterparty identity is present/resolvable according to the
existing event contract. No free-form descriptor may be promoted to
counterpartyId inside SPEC-003.1.
```

Isso evita que o Antigravity invente uma normalização própria.

**Não criaria novo REQ.** Continua sendo `I-SUB-011`.

---

## 2. 🔴 `TASK-3.1.10` está misturando ingestão, engine e persistência

Hoje:

> inject `RecurrencePatternEngine` and `SubscriptionDao`, persisting updated subscription state...

Isso pode resultar em um `SpendingEventListener` fazendo:

```text
event
 ↓
filter
 ↓
dedupe
 ↓
cluster
 ↓
calculate statistics
 ↓
persist
```

e virar justamente o tipo de orchestration class que queremos evitar.

Eu deixaria a responsabilidade assim:

```text
SpendingEventListener
    ↓
qualify / map observation
    ↓
RecurrencePatternEngine
    ↓
SubscriptionProjection / result
    ↓
SubscriptionDao
```

O listener **não deve conter matemática nem lifecycle logic**.

A task precisa dizer isso explicitamente.

---

## 3. 🔴 `eventId` deduplication precisa de persistência durable

Esse é o ponto mais importante de consistência.

A task diz:

> Idempotent deduplication via canonical `eventId`

Mas o DDL de `subscriptions` **não possui eventId processado**.

Se o listener fizer algo como:

```java
Set<UUID> processedEvents
```

isso falha em restart.

E o `ApplicationModuleListener` trabalha em cenário de entrega **at-least-once**, então:

```text
event
  ↓
persist subscription
  ↓
process crashes
  ↓
event redelivered
  ↓
N incrementa novamente
```

é exatamente o bug que `I-SUB-008` pretende evitar.

### Eu colocaria isso como MUST antes da implementação

Precisamos de uma decisão concreta sobre o mecanismo de dedupe.

Por exemplo, uma tabela interna:

```text
intelligence_event_processing
-----------------------------
event_id
tenant_id
processed_at
```

com:

```sql
UNIQUE (event_id)
```

ou equivalente integrado à estratégia de persistência.

**Não estou dizendo que essa tabela é obrigatoriamente a solução** — o ponto é que o TASKS precisa exigir **durable idempotency**, não apenas dedupe em memória.

Isso é especialmente importante porque o PLAN-003 já estabeleceu:

> eventId primary, operationId business-level dedupe.

# O que está particularmente bom

### Matemática

Está muito bem especificada.

Especialmente estes testes:

```text
N=3, CV=0       → confidence 1.00 → ACTIVE
N=3, CV=0.30    → confidence 0.70 → ACTIVE
N=3, CV>0.30    → confidence <.70 → CANDIDATE
```

Isso elimina uma enorme quantidade de interpretação subjetiva.

### Price spike

Também ficou excelente:

```text
historical observations
        ↓
      μ_A(t)
        ↓
A_new >= μ_A(t) * 1.05
        ↓
PRICE_SPIKE_DETECTED
        ↓
ACTIVE continua ACTIVE
```

E o teste:

> `$A_new included in baseline → test assertion fails`

é exatamente o tipo de teste anti-regressão que queremos.

### Tenant isolation

Também está corretamente espalhado entre:

```text
event
 ↓
series key
 ↓
DAO
 ↓
REST
```

em vez de tratar tenant apenas como filtro SQL.

Isso está alinhado com o desenho do Modulith e com o que já definimos em `SPEC-003`.
