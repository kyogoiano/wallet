**Bounded context:** `br.com.wallet.copilot`

This should own the **financially meaningful domain capability**, independent of MCP.

### Owns

* `FinancialProposal`
* proposal lifecycle
* proposal persistence
* proposal TTL
* proposal idempotency
* execution identity / `operationId`

* precondition validation
* proposal → domain UseCase bridge
* audit events
* tenant isolation
* deterministic financial/configuration mutation execution

### Does NOT own

* MCP
* Spring AI
* LLM
* Streamable HTTP
* elicitation protocol
* MCP JSON schemas

The core conceptual flow becomes:

```text
AI / MCP / REST / future UI
             │
             ▼
       copilot::api
             │
             ▼
    FinancialProposal
             │
       Human approval
             │
             ▼
   Domain-specific UseCase
```

This makes `FinancialProposal` a **first-class domain primitive**, which is exactly consistent with the earlier history you mentioned.

# Spring Boot 4.2.0-M2 changes the compatibility question

This is the other reason I like the split.

We should explicitly establish:

```text
Spring Boot baseline:
4.2.0-M2
```

and then verify the **compatible Spring AI milestone/version** rather than just adding "Spring AI" to the architecture.

Because the MCP layer is exactly where framework compatibility is likely to move fastest.

So I would put this in **SPEC-004.1**, not SPEC-004:

> The implementation MUST use a Spring AI MCP release compatible with the project's ratified Spring Boot 4.2.0-M2 baseline. Exact Spring AI version is resolved during PLAN-004.1 and MUST be verified through compilation, MCP integration tests, and protocol compatibility tests.

That prevents the architecture spec from becoming tied to a transient Spring AI artifact version.

# One other thing I'd change from my previous recommendation

I would **not make MCP Elicitation `[MUST]` for every mutation**.

Instead:

### MUST

The MCP Gateway **supports** elicitation where the MCP client advertises the capability.

### MUST

Financial mutations always go through:

```text
FinancialProposal
→ human authorization
→ deterministic domain execution
```

### SHOULD

Use MCP Elicitation as the preferred interactive UX for compatible MCP clients.

Why?

Because **MCP capability negotiation matters**. Not every MCP client necessarily supports every elicitation mechanism.

So:

```text
MCP client supports elicitation
        │
        ├── yes → interactive confirmation
        │
        └── no  → proposal created / alternate
                  human approval channel
```

But **lack of elicitation support must never turn into automatic execution**.

That's an important invariant.

# And there is a beautiful security boundary

The most important invariant becomes:

```text
                    MCP
                     │
                     ▼
              "I want to do X"
                     │
                     ▼
             FinancialProposal
                     │
               human approval
                     │
                     ▼
              domain authority
                     │
                     ▼
                financial state
```

Never:

```text
MCP
 ↓
LLM
 ↓
ledger
```

And never:

```text
MCP elicitation accepted
        ↓
direct mutation
```

Instead:

```text
MCP elicitation accepted
        ↓
human authorization recorded
        ↓
proposal execution
        ↓
domain preconditions
        ↓
idempotent operationId
        ↓
financial mutation
```

That is the architecture I'd want to defend in a senior/staff-level design review.

## One more possible split

I **would not split a third spec for Spring AI**.

Keep:

```text
SPEC-004
Financial Copilot domain

SPEC-004.1
MCP Gateway / Spring AI / Elicitation
```

Spring AI is an **implementation technology of the gateway**, not a business capability deserving its own bounded-context specification.

And I would keep **LLM/SLM semantics in SPEC-000.8.1** where possible. SPEC-004.1 should care about *how an agent interacts with Wallet*, not how the model reasons.

So the Phase 4 roadmap becomes nicely compositional:

```text
000.8.1  Typed Decision / Semantic Evaluation
      │
      └──────────────┐
                     │
003.1 Intelligence ─┤
003.2 Cashflow ─────┤
                     ▼
               SPEC-004
           Financial Copilot
                     │
                     ▼
              SPEC-004.1
           MCP Gateway / AI UX
                     │
                     ▼
          External AI Agents
```

**I'd proceed with the split before writing either PLAN.** The next useful step is to rewrite the current SPEC-004 into **SPEC-004 + SPEC-004.1**, preserving the existing IDs where possible and introducing new IDs only where the new boundary genuinely requires them.
