# 📋 Specification: SPEC-001 — Smart Savings Automation (br.com.wallet.savings)

- **Status**: Draft / Clarification
- **Author**: Antigravity Financial Architecture Team
- **Date**: 2026-08-22
- **Target Release / Milestone**: Wallet Service V4 — Phase 1 (First Business Capability)
- **Architectural Mantra**: *"Capabilities observe, analyze, and decide. The Financial Core (ledger) authorizes and executes."*

---

## 1. Intent & Business Value

To introduce **Smart Savings Automation** as the first concrete peer business capability module (`br.com.wallet.savings`) in the Wallet Service. 

Using Spring Modulith application modules and intra-process domain events (`@ApplicationModuleListener`), the `savings` module passively observes banking events (`DepositCompletedEvent`, `TransferCompletedEvent`) and executes automated, deterministic savings strategies without touching the sealed financial ledger internals.

---

## 2. Core Business Strategies & Rules

```
┌────────────────────────────────────────────────────────────────────────┐
│ 1. Round-Up Savings Rule (Micro-Savings)                               │
│    • Triggers on: TransferCompletedEvent (outgoing payments/transfers) │
│    • Logic: Rounds transaction to nearest increment (e.g., R$ 5.00)   │
│    • Example: Spend R$ 47.30 → Round to R$ 50.00 → Save R$ 2.70        │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │
┌──────────────────────────────────▼─────────────────────────────────────┐
│ 2. Income Percentage Sweep Rule (Pay Yourself First)                   │
│    • Triggers on: DepositCompletedEvent (incoming funds)               │
│    • Logic: Allocates fixed percentage (e.g. 10%) to Savings Wallet    │
│    • Example: Deposit R$ 5,000.00 → Auto-save R$ 500.00                │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │
┌──────────────────────────────────▼─────────────────────────────────────┐
│ 3. Threshold Excess Sweep Rule (Balance Ceiling)                       │
│    • Triggers on: DepositCompletedEvent / Balance evaluation           │
│    • Logic: Sweeps any balance exceeding limit L to Savings Wallet     │
│    • Example: Limit R$ 10,000.00, Balance R$ 12,500.00 → Save R$ 2,500 │
└────────────────────────────────────────────────────────────────────────┘
```

## 4. Mathematical & System Invariants

- **`I-SAVINGS-001` (Non-Re-entrant & Loop Prevention)**: Savings sweep transfers dispatched to `ledger.api.TransferFundsUseCase` MUST carry an idempotent `operation_id` derived deterministically from the triggering transaction:
  $$\text{operationId}_{\text{savings}} = \text{SHA256}(\text{sourceOperationId} + \text{ruleId} + \text{SAVINGS\_SWEEP})$$
  The `savings` listener MUST NEVER react to a `TransferCompletedEvent` generated by its own savings sweep.
- **`I-SAVINGS-002` (Zero Direct Ledger Mutation)**: The `savings` module MUST NOT access `br.com.wallet.ledger.internal.*` or mutate `ledger` or `accounts` tables directly (`I-MODULITH-001`). All monetary movement MUST execute via `ledger.api.TransferFundsUseCase` (`I-MODULITH-002`).
- **`I-SAVINGS-003` (Transaction & Fault Isolation)**: A failure or rejection during savings rule evaluation or sweep dispatch MUST NOT abort the primary deposit or transfer transaction that triggered the event.
- **`I-SAVINGS-004` (Source Account Liquidity Protection)**: A savings sweep MUST NOT execute if it would cause the source account balance to drop below zero (`I-BALANCE-002`) or below the minimum retained balance configured in the savings plan.

## 5. Functional Requirements

- **`REQ-SAV-001` (Savings Plan Configuration)**: Users SHALL be able to configure one or more active savings rules per wallet (Round-Up, Percentage Sweep, Balance Threshold).
- **`REQ-SAV-002` (Asynchronous Event Processing)**: The `savings` module SHALL listen for `DepositCompletedEvent` and `TransferCompletedEvent` using `@ApplicationModuleListener`.
- **`REQ-SAV-003` (Deterministic Round-Up Calculation)**: For Round-Up rules, the system SHALL calculate:
  $$\text{sweepAmount} = \lceil \text{amount} / \text{step} \rceil \times \text{step} - \text{amount}$$
  If $\text{amount}$ is an exact multiple of $\text{step}$, $\text{sweepAmount} = 0$.
- **`REQ-SAV-004` (Deterministic Percentage Calculation)**: For Percentage rules, the system SHALL calculate:
  $$\text{sweepAmount} = \text{depositAmount} \times \frac{\text{percentage}}{100}$$
- **`REQ-SAV-005` (Idempotent Sweep Execution)**: Every triggered sweep SHALL invoke `ledger.api.TransferFundsUseCase` with a deterministic `operation_id`.
- **`REQ-SAV-006` (Savings Metrics & History)**: The system SHALL record execution history and provide aggregate metrics (total saved, frequency, breakdown by rule).

---

## 6. Non-Functional Requirements

- **Performance**: Rule evaluation in memory SHALL execute in $< 2\text{ms}$ ($O(1)$).
- **Modularity**: `ApplicationModules.of(WalletApplication.class).verify()` MUST confirm clean dependencies: `savings` $\rightarrow$ `ledger::api`, `core::api`.
- **Observability**: Every savings sweep MUST participate in the active OpenTelemetry trace context, adding baggage `savings.rule_id` and `savings.source_operation_id`.

```java
package br.com.wallet.savings.internal.listener;

import br.com.wallet.ledger.api.event.DepositCompletedEvent;
import br.com.wallet.ledger.api.event.TransferCompletedEvent;
import org.springframework.modulith.events.ApplicationModuleListener;

public class SavingsEventListener {

    @ApplicationModuleListener
    public void onDeposit(DepositCompletedEvent event) {
        // Evaluate percentage and threshold sweep rules
    }

    @ApplicationModuleListener
    public void onTransfer(TransferCompletedEvent event) {
        // Evaluate round-up rule (skip if event is already a savings sweep)
    }
}
```

## 8. Failure Modes & Edge Cases

| Scenario | Expected Behavior | Invariant Enforced |
| :--- | :--- | :--- |
| Savings sweep fails due to insufficient funds | Sweep is marked skipped in savings log; primary transaction is NOT rolled back | `I-SAVINGS-003`, `I-SAVINGS-004` |
| Event received for self-generated savings transfer | Event is ignored immediately based on `operation_id` tagging | `I-SAVINGS-001` (Loop prevention) |
| Target savings wallet does not exist or is locked | Exception caught, logged, and alert emitted; primary transaction unaffected | `I-SAVINGS-003` |
| Direct import of `br.com.wallet.ledger.internal.AccountDao` | Architecture verification fails during build | `I-SAVINGS-002`, `I-MODULITH-001` |
